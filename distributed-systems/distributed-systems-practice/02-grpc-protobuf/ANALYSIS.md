# ANALYSIS — what's real, what's simulated, and why

## The honest boundary

**Real, unmodified, verified:**
- `proto/telemetry.proto` — a genuine Protocol Buffers schema, including
  a real `service` block using gRPC's own IDL syntax (`rpc`, `stream`).
- `gen/telemetry_pb2.py` — generated by the actual `protoc` compiler
  (v28.3, fetched from the official GitHub release — see "How this
  environment was built" below), not hand-written or faked.
- Every byte on the wire for a message is produced by
  `<Message>.SerializeToString()` from the real `protobuf` Python
  runtime, and parsed back with real `.ParseFromString()` — genuine
  Protocol Buffers wire format, interoperable with any other protobuf
  implementation reading the same schema.

**Hand-rolled, standing in for the real thing:**
- `rpc/framing.py` and `rpc/rpc_base.py` — the TCP transport that moves
  those real messages between processes, and the client/server call
  plumbing for the four RPC shapes. In a real gRPC stack, this entire
  layer is gRPC itself: HTTP/2 framing, stream multiplexing over one
  connection, flow control, header compression, deadlines, and
  generated client/server stub code from a `--grpc_out` protoc plugin.

The `service` definition in the `.proto` file is real and would compile
cleanly with a real `protoc --grpc_out` run — it just wasn't actually
run through that plugin here, because the plugin isn't available in this
environment (see below). The handlers in `server.py` and the call
wrappers in `client.py` are what that plugin's generated code would
otherwise have produced for you.

## Why not just install gRPC?

This was tested, not assumed. In order:

1. **apt** — blocked outright. `apt-get update` gets `403 Forbidden` from
   every Ubuntu mirror through this sandbox's network proxy. No
   `libgrpc++-dev` / `protobuf-compiler-grpc` route.
2. **pip** — `pip install grpcio` (and every version tried, old and new)
   returns `No matching distribution found`, even though `pip install
   requests` / `numpy` / `protobuf` all work fine. The pure-Python
   `protobuf` package is available; the large, platform-specific
   `grpcio` C-extension wheel is not, in this sandbox's package index.
3. **npm** — blocked entirely in this session (even `npm install lodash`
   gets `403 Forbidden` from the registry), ruling out the pure-JS
   `@grpc/grpc-js` route, which would otherwise have sidestepped the
   native-extension problem.
4. **Build protobuf's C++ runtime from source** — technically possible
   (GitHub itself is reachable), but was deliberately not attempted:
   protobuf's C++ build now depends on Abseil, this container has only 2
   CPU cores, and a from-source build of both libraries is a multi-minute,
   non-trivial-to-debug undertaking with a real chance of failing on a
   missing transitive dependency partway through — a bad trade for a
   teaching exercise whose point is RPC semantics, not fighting a build.
5. **A standalone `protoc` binary** — this one worked. GitHub release
   downloads aren't blocked, so the compiler itself (not the gRPC
   runtime) was fetched directly and verified end-to-end (round-tripped
   a real message through real generated code) before building anything
   else on top of it.

So: real protobuf, real schema, real compiler, hand-rolled transport.
That's a deliberate, tested conclusion, not a guess.

## Mapping onto what gRPC actually provides

| gRPC feature | Here | Gap |
|---|---|---|
| 4 RPC shapes (unary/server-stream/client-stream/bidi) | **Implemented**, all 4, each independently tested | None at the semantic level |
| Message serialization | **Real protobuf**, byte-for-byte what gRPC would produce | None |
| Service/method routing | Hand-rolled (`Dispatcher` + method-name string in `CALL_START`) | gRPC uses HTTP/2 `:path` pseudo-headers (`/package.Service/Method`); same idea, different envelope |
| Transport | One TCP connection per RPC call | gRPC multiplexes many concurrent RPCs over **one** HTTP/2 connection, each as its own HTTP/2 stream — far better connection reuse and far less per-call handshake overhead |
| Flow control | None — `send_frame` just calls `sendall` | HTTP/2 has real backpressure (window updates) so a fast sender can't overrun a slow reader; a sufficiently fast bidi producer here could, in principle, fill OS socket buffers with nothing upstream slowing it down |
| Deadlines / cancellation | None | gRPC lets a client set a deadline and propagate cancellation through the whole call chain; here a hung handler just hangs the connection forever |
| Status codes | One generic `ERROR` frame with a string | gRPC has a structured status-code enum (`NOT_FOUND`, `UNAVAILABLE`, `DEADLINE_EXCEEDED`, ...) client code can branch on programmatically |
| Auth / interceptors / load balancing / retries / reflection | None | All standard, production-grade gRPC features with no equivalent here |
| Generated client/server stubs | Hand-written (`client.py`, `server.py`) | A real `protoc --grpc_out` run generates both sides' boilerplate automatically from the same `.proto` — editing the schema here means hand-updating the handlers too, which a real toolchain wouldn't require |

The takeaway: the parts of gRPC this project set out to teach — what a
`.proto` schema looks like, what each of the four call shapes means for
how requests and responses flow, and how a service implementation plugs
into that — are genuinely present and genuinely exercised. The parts
it does *not* attempt to reproduce are specifically the ones that come
from gRPC sitting on top of HTTP/2 and a mature multi-language codegen
pipeline, which is a reasonable scope cut for a single sandboxed
teaching exercise and is exactly why it's spelled out here rather than
left implicit.

## Design notes on the hand-rolled transport

**Why a fresh connection per call, except for streams.** Unary and
server-streaming calls use one connection for their single request;
client-streaming and bidi calls need a connection held open for the
duration of the stream, since requests arrive over time. This project
always opens one connection per logical call (never reuses one
connection across multiple separate RPCs) — simpler to reason about, at
the cost of TCP handshake overhead per call that gRPC's multiplexing
would avoid. This mirrors the same trade-off made explicitly in Project
1 (Raft)'s wire protocol.

**Why bidi streaming needs a reader thread.** A single TCP socket is
full-duplex, but a single Python thread can't block on "read the next
frame" and "the handler wants to write a frame" at the same time. The
server's bidi handling spawns a dedicated reader thread that pulls
incoming `DATA` frames off the socket and feeds them into a queue; the
main handler thread consumes that queue (via a generator) and writes
responses to the socket as its own handler generator yields them. This
is the same consumer/producer split real async gRPC runtimes handle via
an event loop instead of a thread — a thread-per-direction is the
simplest correct version of the same idea.

**Why handlers are generators for streaming RPCs.** `stream_alerts` and
`control_channel` are Python generator functions: they `yield` each
response as it becomes available rather than building a list and
returning it all at once. This is what actually makes it *streaming* —
the server can start sending the first response before it has computed
the last one, and the dispatcher writes each one to the socket the
moment it's yielded. A real generated gRPC servicer uses exactly this
shape (a generator, or an async generator) for its own streaming
methods.

## What was actually verified

- All four RPC shapes, run end-to-end through `scripts/demo.sh`, 5
  consecutive times with no failures.
- 6 concurrent clients hitting one server simultaneously (each running
  all four RPCs), to exercise the per-connection threaded dispatcher
  under real concurrency — all 6 completed successfully with no
  cross-talk between connections (each client's `UploadReadings` summary
  was independently checked against what that specific client actually
  sent, not just "some" summary).
- The client-streaming summary's `count`/`avg` are asserted in
  `client.py` against the values the client itself generated — not just
  printed and eyeballed — so a server-side aggregation bug would fail
  the demo, not just produce suspicious-looking output.
