## The command

```
grep "hello" file.txt | sort > result.txt
```

Chosen deliberately: it exercises quoting, a pipeline, redirection on only one side of that pipeline, and two commands with genuinely different internal shapes — one streaming, one not.

---

## The complete trace

**1. Keystrokes.** Every character — `g`, `r`, `e`, `p`, space, `"`, `h`, `e`, `l`, `l`, `o`, `"`, space, `f`, `i`, `l`, `e`, `.`, `t`, `x`, `t`, space, `|`, space, `s`, `o`, `r`, `t`, space, `>`, space, `r`, `e`, `s`, `u`, `l`, `t`, `.`, `t`, `x`, `t`, Enter — generated by hardware, becomes a GUI key event.

**2. Terminal emulator.** Converts each key event to bytes, `write()`s them to the PTY master (file 01).

**3. Line discipline, canonical mode.** Echoes each character back immediately — you see it on screen before the shell has read anything — and buffers the whole line (file 02).

**4. Enter.** The line discipline delivers the complete, assembled line to the shell's blocked `read()` on fd 0 (file 02).

**5. Shell parsing (file 06).** Tokenization recognizes `grep`, `"hello"` (one quoted token), `file.txt`, the `|` operator (a shell metacharacter, splitting this into **two** simple commands joined by a pipeline), `sort`, the `>` operator, `result.txt`. Quote removal strips `"hello"` down to the literal `hello`. No `$`/glob characters appear anywhere, so expansion finds nothing to do for either command. Result: a two-command pipeline — `grep hello file.txt` and `sort`, with `sort`'s stdout additionally redirected to `result.txt`.

**6. Command lookup and `PATH` search (file 07).** Neither `grep` nor `sort` is a builtin, alias, or function in a typical setup — the shell searches `$PATH` for each, finds them (commonly `/usr/bin/grep`, `/usr/bin/sort`), and caches both locations in its hash table for next time.

**7. Pipe creation (file 13).** The shell calls `pipe()` **once**, obtaining `fds[0]` (read) and `fds[1]` (write) — before either child exists, so both about-to-be-forked children will inherit copies.

**8. First `fork` — the `grep` child (file 08).**
- `dup2(fds[1], STDOUT_FILENO)` — `grep`'s stdout now points at the pipe's write end (files 10, 13).
- Closes both original pipe fds in this child (file 13's discipline).
- `grep`'s **stdin is untouched** — it reads `file.txt` as a named argument, not via stdin, so no redirection is needed there at all.
- `execve("/usr/bin/grep", ["grep", "hello", "file.txt"], envp)` (files 08-09).
- **ELF loader:** kernel maps `grep`'s text/rodata/data/BSS, builds a fresh stack with `argv`/`envp`; for a dynamically linked `grep`, `ld.so` runs *first*, resolving `libc.so` and any other dependencies, before `grep`'s own `main()` ever executes (file 08).

**9. Second `fork` — the `sort` child (file 08).**
- `dup2(fds[0], STDIN_FILENO)` — `sort`'s stdin now points at the pipe's read end.
- **Additionally:** `sort`'s stdout needs redirecting to `result.txt` (file 12) — `open("result.txt", O_WRONLY|O_CREAT|O_TRUNC)`, then `dup2()` that fd onto `STDOUT_FILENO`.
- Closes both original pipe fds in this child too.
- `execve("/usr/bin/sort", ["sort"], envp)`, with the identical ELF-loading/dynamic-linking sequence as step 8, for `sort`'s own binary.

> **Remember**
> Steps 8 and 9's two `dup2` calls in `sort`'s child touch **different fd numbers** (0 and 1) — this is not an instance of file 11's `2>&1` order-dependence trap, which only applies when multiple redirections target the *same* fd. Order between these two doesn't matter.

**10. Shell closes its own original pipe fds (file 13, Section 6).** Critical: without this, `sort`'s read end would never see EOF, no matter how completely `grep` finishes.

**11. Shell calls `waitpid()` for both children (file 08)** — blocks, doing nothing else, until both report back.

**12. Filesystem (file 19).** `grep`'s process calls `openat("file.txt", O_RDONLY)`, then loops `read()`/pattern-check/`write()`. For each line read, `grep` checks it against `"hello"` — entirely its own application-level logic; the kernel has no concept of "a pattern" at all. Matching lines are `write()`'d to fd 1 — the pipe's write end, not the terminal, because of step 8's `dup2`.

**13. The pipe, streaming (files 13, 22).** Matching lines flow through the kernel's pipe buffer from `grep`'s writes to whatever `sort`'s reads can consume, as both processes run — genuinely concurrently, some blend of real parallelism and scheduler time-slicing depending on available cores (file 22), exactly as file 13 originally described in the abstract.

**14. `sort` buffers its entire input.** Here's a genuine algorithmic difference worth naming explicitly: unlike `grep` or `cat`, which can stream line by line, `sort` **must see every line before it can correctly order any of them** — it is not a line-at-a-time streaming tool. It keeps reading until `grep` exits, every copy of the pipe's write end closes, and its `read()` finally returns `0` — the same EOF mechanism as everywhere else in this handbook (file 13).

**15. `sort` sorts and writes.** The sort itself is pure userspace computation, no syscalls involved. The result is `write()`'d to fd 1 — which, because of step 9's redirection, is now `result.txt`, not a pipe or a terminal (files 09, 11, 12).

**16. `grep` exits (file 08).** Its exit status reflects whether it found any matches: `0` if at least one line matched, `1` if none did, `2` on an actual error (a real, precise detail specific to `grep`'s own convention).

**17. `sort` exits**, once it's finished writing `result.txt`, with its own exit status (typically `0` on success).

**18. The shell's `waitpid()` calls wake up**, one at a time, as each child actually finishes (not necessarily in the order they were started) — retrieving each exit status.

> **Remember**
> `$?` after a pipeline reflects, **by default, the *last* command's exit status** — `sort`'s, not `grep`'s — unless `set -o pipefail` is active (file 42 preview). A pipeline where `grep` found nothing but `sort` still ran successfully reports success via `$?`, which surprises people relying on `grep`'s own exit code to signal "no matches."

**19. Shell prints its next prompt** — the identical fd 1 → PTY slave → master → terminal emulator → screen path from every earlier output in this trace — and loops back to `read()` on fd 0, waiting for whatever you type next.

## The final picture

```
Shell
 |
 +-- fork -> grep   (stdout -> pipe write end; reads file.txt directly as an argument)
 |             |
 |          [ PIPE ]
 |             |
 +-- fork -> sort   (stdin -> pipe read end; stdout -> result.txt)
```

## What this trace proves, as a whole

- **Nothing in this entire sequence involved the kernel understanding "hello," "grep," "sort," or any application-level concept whatsoever.** Every kernel-level step is generic: open a file, read bytes, write bytes, create a process, wire up descriptors. All meaning — pattern matching, sorting — is userspace code, running in two ordinary processes the shell happened to launch.
- **The two commands have genuinely different internal shapes** — one streaming, one buffering — invisible from the shell's point of view, which treats both identically as "a process connected to some fds."
- **Every single mechanism in this trace was fully explained, with working code, in an earlier file.** This chapter assembled them; it introduced nothing new.
