## 0. The program these tools are run against

```c
/* util.h */
#ifndef UTIL_H
#define UTIL_H
int square(int x);
extern int call_count;
#endif

/* util.c */
#include "util.h"
int call_count = 0;
static int helper(int x) { return x * x; }
int square(int x) { call_count++; return helper(x); }

/* main.c */
#include <stdio.h>
#include "util.h"
static const char *banner = "square demo";
int uninit_global;            /* .bss */
int init_global = 7;          /* .data */
int main(void) {
    printf("%s: %d\n", banner, square(init_global));
    return uninit_global;
}
```

Built with `gcc -c util.c -o util.o`, `gcc -c main.c -o main.o`, `gcc main.o util.o -o demo`.

## 1. `nm` — the symbol table, made readable

`[External, real output]`

```
$ nm util.o
0000000000000000 B call_count
0000000000000000 t helper
0000000000000013 T square

$ nm main.o
0000000000000000 d banner
0000000000000000 D init_global
0000000000000000 T main
                 U printf
                 U square
0000000000000000 B uninit_global
```

### 🎯 This is Phase 2's `static` rule, made visible

`[Synthesis]` The letter case is the whole story: **uppercase = external (global) linkage,
lowercase = internal (`static`) linkage** — exactly `functions/01_functions_and_stack_frames.md`
§5's distinction, now read directly off a real binary instead of taken on faith. `helper`
(declared `static` in the source) shows as lowercase `t`; `square` (not `static`) shows as
uppercase `T`. Same pattern for data: `banner` (`static const char *`) is lowercase `d`;
`init_global` is uppercase `D`.

### The other letters, read from this real output

| Letter | Meaning | Example above |
|---|---|---|
| `T`/`t` | Defined in `.text` (code), global/local | `square`, `main` / `helper` |
| `D`/`d` | Defined in `.data` (initialized), global/local | `init_global` / `banner` |
| `B`/`b` | Defined in `.bss` (zero-initialized), global/local | `call_count`, `uninit_global` |
| `U` | **Undefined** — referenced here, defined elsewhere | `printf`, `square` (in `main.o`) |

`main.o` shows `square` as `U` — undefined — because `main.c` only has `util.h`'s
*declaration*; the *definition* lives in `util.o`. This is
`fundamentals/01_program_structure.md` §4's declaration/definition split, and
`systems/02_linking_and_loading.md` §1's "symbol resolution" step, both made literal: the
linker's whole job on this file is turning that one `U` into a real address.

## 2. `size` — the section byte-counts, at a glance

`[External, real output]`

```
$ size main.o util.o demo
   text	   data	    bss	    dec	    hex	filename
    169	     12	      4	    185	     b9	main.o
    181	      0	      4	    185	     b9	util.o
   1580	    616	     16	   2212	    8a4	demo
```

`[Synthesis]` `main.o`'s `bss` column shows `4` — exactly `sizeof(int)` for
`uninit_global` — confirming `systems/01_compilation_toolchain.md` §3's claim directly:
the object file records a **size**, not literal zero bytes, for that variable. `demo` (the
fully linked executable) is far larger in every column than the sum of the two `.o` files,
because linking pulls in C-runtime startup code and (statically-linked pieces of) the
library support `main` needs — the "hidden" code between `./program` and your own `main`
that `systems/02_linking_and_loading.md` §6 described.

## 3. `readelf`/`objdump` — relocations, made completely literal

`[External, real output — this is the single most concrete illustration in this vault of
`systems/02_linking_and_loading.md` §3's relocation discussion]`

```
$ objdump -d -r -M intel main.o
...
  10:	e8 00 00 00 00       	call   15 <main+0x15>
			11: R_X86_64_PLT32	square-0x4
...
```

**Read this literally, byte by byte.** `e8` is the x86-64 `call` opcode; `00 00 00 00` — four
zero bytes — is the **destination address, not yet known**. The line right below,
`R_X86_64_PLT32 square-0x4`, is the **relocation entry**: it tells the linker *"once you
know `square`'s real address, compute the correct PC-relative offset and write it into
these four zero bytes, right here."* This is not an abstraction — it is the literal
placeholder `systems/02_linking_and_loading.md` §3 described, visible as four real zero
bytes in a real compiled file, waiting to be patched.

`readelf -r` shows the same information more exhaustively, across every relocatable
section:

```
$ readelf -r -W main.o
Relocation section '.rela.text' at offset 0x260 contains 6 entries:
    Offset             Info             Type               Symbol's Value  Symbol's Name + Addend
000000000000000a  0000000700000002 R_X86_64_PC32          0000000000000000 init_global - 4
0000000000000011  0000000900000004 R_X86_64_PLT32         0000000000000000 square - 4
0000000000000031  0000000a00000004 R_X86_64_PLT32         0000000000000000 printf - 4
0000000000000037  0000000200000002 R_X86_64_PC32          0000000000000000 uninit_global - 4
```

`[Synthesis]` `square` and `printf` (function calls) use `R_X86_64_PLT32`;
`init_global`/`uninit_global` (data references) use `R_X86_64_PC32` — different relocation
*types* for the same underlying idea, because the CPU instructions that reference code vs.
data are encoded slightly differently. You don't need to memorize the type names; the
point is that **every single symbolic reference this file makes to something outside
itself** — every function call, every external variable access — left behind exactly one
relocation entry, and you can now literally count them (six, in `.rela.text` alone).

`readelf -S` shows the section table this all lives in — `.text`, `.data`, `.bss`,
`.rodata`, `.symtab`, matching `systems/01_compilation_toolchain.md` §3's table exactly,
now with real sizes and offsets instead of a description.

## 4. `strings` — finding text inside a binary without disassembling it

`[External, real output]`

```
$ strings -n 4 main.o
square demo
%s: %d
GCC: (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0
main.c
banner
uninit_global
main
square
printf
.symtab
.strtab
...
```

`strings` prints every sequence of printable characters at least `-n` bytes long, wherever
it finds one — no understanding of the file format at all. Notice it surfaces **both**
genuinely useful application data (the format string `%s: %d`, the literal `square demo`)
**and** incidental noise (section names, compiler version strings) — reading `strings`
output is a skill of filtering signal from this kind of noise, not a precise query.
`libraries/01_stdio.md` §1's claim that string literals live in `.rodata`
(`memory/04_arrays_and_strings.md` §4) is exactly why `"square demo"` shows up here at all:
it's stored as literal bytes in the file, unlike a computed value.

## 5. `file` and `ldd` — what kind of thing is this, and what does it need?

`[External, real output]`

```
$ file demo
demo: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked,
interpreter /lib64/ld-linux-x86-64.so.2, ... not stripped

$ file util.o
util.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
```

`file` identifies a binary's format by inspecting its actual header bytes, not its
extension — note it correctly distinguishes `demo` ("executable") from `util.o`
("relocatable") — exactly `systems/01_compilation_toolchain.md` §2's pipeline distinction
between "not yet linked" and "ready to run," confirmed from the file itself.

```
$ ldd demo
	linux-vdso.so.1 (0x00007f9577f20000)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f9577c00000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f9577f22000)
```

This is `systems/02_linking_and_loading.md` §5's dynamic linker's own search results, made
visible: `demo` depends on `libc.so.6` (found, with its runtime load address) and is
itself interpreted by `ld-linux-x86-64.so.2` — precisely the "not found" diagnostic
`02_linking_and_loading.md` §5 previewed, now shown for the successful case.

## 6. The two classic linker errors, verbatim

`[External, real output — the exact scenarios `systems/02_linking_and_loading.md` §2
described abstractly, now reproduced]`

### "undefined reference"

```
$ gcc badmain.o util.o -o baddemo
/usr/bin/ld: badmain.o: in function `main':
badmain.c:(.text+0x24): undefined reference to `not_declared_anywhere'
collect2: error: ld returned 1 exit status
```

### "multiple definition"

```
$ gcc a.o b.o -o dup_demo
/usr/bin/ld: b.o:(.data+0x0): multiple definition of `shared_val'; a.o:(.data+0x0): first defined here
collect2: error: ld returned 1 exit status
```

`[Synthesis]` Both errors name the **exact object file and offset** — `nm` on the same
`.o` files (§1) would show the offending symbol as `U` (undefined reference case) or as two
separate `D`/`B` definitions across two files (multiple-definition case), giving you a
direct, tool-based way to diagnose either error rather than reasoning about it purely from
the message text.

## 7. ⚠️ Misconceptions to unlearn now

- **"You need to read assembly fluently to get anything from `objdump`."** `objdump -d -r`
  is readable at the level shown in §3 — the opcode bytes matter less than the relocation
  annotation right below each call/reference.
- **"`strings` only finds 'real' strings the program uses."** It finds *any* sufficiently
  long printable byte sequence, including compiler metadata and section names — genuine
  application strings are mixed in with noise (§4).
- **"A `.o` file and an executable are basically the same kind of file."** `file` can and
  does distinguish them by their actual ELF type field (`relocatable` vs. `executable`) —
  a real, checkable difference, not just a naming convention (§5).

## 8. 🎯 Interview questions

**Easy**
- In `nm` output, what does a lowercase symbol letter (`t`, `d`, `b`) mean versus
  uppercase? → Internal (`static`) linkage vs. external (global) linkage (§1).
- What does `U` mean in `nm` output? → The symbol is referenced but not defined in this
  object file — the linker must resolve it elsewhere (§1).

**Medium**
- Why does `main.o`'s `size` output show a nonzero `bss` column even though the file
  itself doesn't grow to hold that memory? → `.bss` records only a size, not literal zero
  bytes — `systems/01_compilation_toolchain.md` §3's "BSS trick," directly confirmed (§2).
- Why do function-call relocations (`square`, `printf`) use a different relocation type
  (`R_X86_64_PLT32`) than data references (`init_global`)? → The CPU encodes code-address
  and data-address references slightly differently, so the linker needs to know which kind
  of patch to apply (§3).

**Hard**
- Walk through exactly what the four zero bytes after a `call` opcode in an unlinked
  object file represent, and how the linker resolves them. → They're a placeholder for the
  call target's address, not yet known because the target (e.g. `square`) is defined in a
  different translation unit; the accompanying relocation entry names the target symbol and
  the patching method, and the linker overwrites those exact bytes once it has resolved
  that symbol's real address (§3).
- Given only `nm` output for two object files, how could you predict a "multiple
  definition" error before even attempting to link them? → Look for the same symbol
  appearing as a defined type (`D`/`B`/`T`, uppercase — external linkage) in *both* files;
  two external definitions of the same name will conflict at link time (§1, §6).

**Systems-level**
- A teammate's build fails with "undefined reference to `foo`" despite `foo` clearly being
  defined in the project. What two `nm`-based checks would you run first? → `nm` on the
  object file that's supposed to define `foo`, to confirm it actually shows as a defined
  (uppercase) symbol and not accidentally `static` (lowercase, invisible outside its file);
  and `nm` on the object file calling it, to confirm the reference is really there as `U`
  and correctly spelled (§1, §6).
- `ldd` reports every dependency for `demo` as found, but the program still fails at
  startup with a symbol-resolution error. What layer of `systems/02_linking_and_loading.md`
  §5 does this point to? → The dynamic linker found and mapped every *library*
  successfully, but a specific *symbol* it expected inside one of them is missing or has an
  incompatible version — a finer-grained failure than "library not found," often caused by
  a version mismatch between the library the program was built against and the one
  actually installed (§5).
