# Chapter 10 — Networking (Part 3 of 3: UDP, DNS, IP, Qdiscs, Devices, and Wrap-Up)

*Study notes on Chapter 10 of BPF Performance Tools (Brendan Gregg, 2019). Original notes, not book text — see `00-index.md` for how these notes are written. Continues directly from Parts 1–2 (background/traditional/socket tools, and the nine TCP tools).*

## 10.3.20 `udpconnect` — connected UDP only

Traces new UDP connections that use `connect(2)` — which, for UDP, doesn't establish a real session the way TCP's handshake does; it just lets the socket skip re-specifying a destination address on every subsequent `send()`. **Unconnected UDP (using `sendto()` per-packet with no prior `connect()`) is explicitly not traced by this tool at all** — a real, named scope limitation worth remembering rather than assuming this tool sees all UDP traffic. Kprobes `ip4_datagram_connect()`/`ip6_datagram_connect()` — the `.connect` members of `udp_prot`/`udpv6_prot`, the same struct-callback pattern Part 1's `soprotocol(8)` reads its protocol name from. The book explicitly points to `socketio(8)` (Part 1) as the tool to reach for general UDP send/receive visibility instead, and suggests a dedicated `udp_sendmsg()`/`udp_recvmsg()`-based tool as a natural extension if you specifically want UDP isolated from all other socket traffic's overhead.

## 10.3.21 `gethostlatency` — DNS resolution latency, and a real Shopify production incident

Traces resolver library calls (`getaddrinfo()`, `gethostbyname()`, `gethostbyname2()`) via uprobes on libc, printing per-call latency and the hostname being resolved. A real example shows resolution times ranging from 2.6 ms (likely cache-served) up to **279 ms** for one specific lookup — direct, quantified evidence for §10.1.3's strategy step 5 ("DNS is a common, easily-overlooked source of production latency"). **A real, named production story worth remembering as a model investigative arc**: at Shopify, this exact tool (bpftrace version) was run across a Kubernetes cluster to characterize a DNS latency issue — the data specifically **did not** implicate any particular server or lookup target (ruling out the obvious first suspects), but instead correlated with **how many lookups were in flight simultaneously** — eventually traced to a **cloud provider's limit on concurrent UDP sessions per host**. Increasing that limit resolved the issue. **The mechanically interesting part, worth remembering as a real, named limitation**: since it uprobes a *specific, hardcoded libc path* (`/lib/x86_64-linux-gnu/libc.so.6`), it won't work unmodified against a different resolver library, a statically-linked binary, or an application implementing its own resolution logic — a concrete instance of uprobes' Chapter 2 file-based-not-process-based semantics cutting the other way (you have to know exactly *which* file to target).

## 10.3.22 `ipecn` — inbound ECN, presented candidly as a proof of concept

Traces inbound IPv4 **Explicit Congestion Notification (ECN)** "Congestion Encountered" events by kprobing `ip_rcv()` and manually parsing the IP header's ToS byte. **The book's own framing of this tool is worth remembering as a model of intellectual honesty about a tool's limitations, rather than overselling it**: because `ip_rcv()` fires on *every* received packet just to check two bits, the author explicitly calls this "not ideal" and "more of a proof of concept" — the better approach (instrumenting only the specific, rare CE-handling code path) wasn't available because that logic was **inlined** and had no separately callable/traceable function on the kernel version used, and no dedicated tracepoint exists for this event at all. ECN itself matters because DCTCP (DataCenter TCP) congestion control uses it directly, and switches/routers (or, for testing, Linux's own `netem` qdisc) can set it to signal congestion without actually dropping a packet.

## 10.3.23 `superping` — validating what `ping(8)` itself reports

Measures ICMP echo request-to-reply latency **from inside the kernel network stack directly**, specifically to sanity-check `ping(8)`'s own reported numbers. **The reason this is a real, non-redundant measurement, worth understanding precisely**: older `ping(8)` implementations (or any system lacking `SO_TIMESTAMP`/`SIOCGSTAMP` socket-timestamp support) measure round-trip time from **user space**, which means the number includes **CPU scheduling latency** for the `ping` process itself — on a busy, contended system, this can meaningfully inflate the reported RTT above the network's true latency. The book's own side-by-side demonstration (forcing old-style behavior via `ping -U`) shows measured times inflated by **over 0.10 ms** versus `superping`'s kernel-level measurement — with modern socket-timestamped `ping` runs, the gap shrinks to within about 0.01 ms. Keys its timestamp map by the ICMP **(identifier, sequence number)** pair — yet another instance of "find a stable, event-appropriate key when thread ID won't work," alongside Chapter 9's request-address key and this chapter's own `struct sock`-pointer key.

## 10.3.24–10.3.25 `qdisc-fq` and its siblings — one tool, six substitutions

**`qdisc-fq(8)`** times packets queued in the **Fair Queue (FQ)** qdisc by kprobing `fq_enqueue()`'s entry (keyed by the `sk_buff` pointer, `arg0`) and `fq_dequeue()`'s return (keyed by `retval`, since the dequeued `sk_buff` is what's *returned*) — a real production example shows the overwhelming majority of packets queued under 4 μs, with a small long tail reaching into the low milliseconds. **A genuinely practical gotcha worth remembering**: this tool only works while the FQ scheduler is actually loaded/active — if it's not, you'll see a plain `cannot attach kprobe, Invalid argument` error, fixed with `modprobe sch_fq` (though the book notes correctly that if FQ genuinely isn't in use, there's nothing to measure regardless). **The genuinely reusable technique here**: every Linux qdisc scheduler implements the *same* `struct Qdisc_ops` interface (`.enqueue`/`.dequeue` function pointers, defined in `include/net/sch_generic.h`) — meaning the *entire* `qdisc-fq.bt` script can be adapted to any other scheduler just by swapping which two named functions you kprobe, since they all share this identical calling convention. The book supplies the substitution table directly:

| Tool | Qdisc | Enqueue function | Dequeue function |
|---|---|---|---|
| `qdisc-cbq.bt` | Class Based Queueing | `cbq_enqueue()` | `cbq_dequeue()` |
| `qdisc-cbs.bt` | Credit Based Shaper | `cbs_enqueue()` | `cbs_dequeue()` |
| `qdisc-codel.bt` | Controlled-Delay AQM | `codel_qdisc_enqueue()` | `codel_qdisc_dequeue()` |
| `qdisc-fq_codel.bt` | Fair Queueing + Controlled Delay | `fq_codel_enqueue()` | `fq_codel_dequeue()` |
| `qdisc-red.bt` | Random Early Detection | `red_enqueue()` | `red_dequeue()` |
| `qdisc-tbf.bt` | Token Bucket Filter | `tbf_enqueue()` | `tbf_dequeue()` |

The book even suggests, as a natural next step, wrapping this whole pattern in a shell script (`qdisclat`) that takes a qdisc name as an argument and generates the matching bpftrace program on the fly — a nice small example of "the tool itself could generate other tools."

## 10.3.26 `netsize` — packet sizes before/after offload, and another stark BPF-vs-userspace efficiency comparison

Histograms packet sizes at **two different layers simultaneously**: the kernel network stack's own send/receive path (`net:netif_receive_skb`, `net:net_dev_queue`) versus the **NIC-facing** path after segmentation offload (`net:napi_gro_receive_entry`, `net:net_dev_xmit`). A real production example shows receives clustering under 64 bytes, while sends cluster in the 8–64 KB range at the stack level but drop to a 1–2 KB range at the NIC level — direct, measured evidence of **GSO** actively splitting large "super-packets" down to MTU-sized segments before hardware transmission (and the book notes that if TSO were active instead, the NIC-level histogram would *also* show large sizes, since segmentation would then happen in hardware, after this tool's instrumentation point). **A second, very clean, directly-measured BPF-efficiency comparison is given here, in the same spirit as Chapter 8's `fatrace`/`opensnoop` comparison**: running `iptraf-ng` (a traditional, packet-sniffing, userspace-processing tool) against a live `iperf` benchmark showed it consuming **over 90% of one CPU**; running `netsize.bt` against the identical benchmark showed **0% CPU** in `pidstat`'s own measurement — the book's own blunt conclusion: "This highlights a key difference between the approaches."

## 10.3.27 `nettxlat` — device transmit-queue latency, and a real timestamp-reuse bug fix shown in the source

Times from a packet being handed to the device queue (`net:net_dev_start_xmit`) to the driver/hardware signaling completion (`skb:consume_skb`, freeing the packet) — a production example shows this usually completing in under 128 μs. **The source contains a genuinely instructive defensive-programming detail worth understanding, not just noting**: because some packets can take an alternate code path that never reaches `skb:consume_skb` at all, a *later, unrelated* `sk_buff` could theoretically be allocated at the exact same memory address and incorrectly inherit a stale timestamp from the earlier, never-cleaned-up entry — producing a bogus, huge latency outlier in the histogram. The fix, visible directly in the source: an extra probe on `net:net_dev_queue` whose entire job is to **proactively delete** any existing timestamp for that address *before* a new one might need to be recorded — a small, general, reusable pattern for any tool where an event pair might not always complete cleanly. **Extending it to break down by device name** (`nettxlat-dev.bt`) is shown as a minimal three-line diff — but the book flags this specific extension as a real stability tradeoff worth being conscious of: reading `$skb->dev->name` means depending on `struct sk_buff`'s internal layout directly, not just on tracepoint arguments, making the extended version meaningfully more fragile to future kernel changes than the original.

## 10.3.28 `skbdrop` — unusual packet drops, correlated automatically against `nstat`

Traces `skb:kfree_skb` (**not** the normal-path `skb:consume_skb` — `kfree_skb` specifically fires for *unusual*, worth-investigating drop events) and captures the kernel stack trace at each one, while also automatically running `nstat` counters for the same duration via `system()` calls in its own `BEGIN`/`END` blocks. A real example cross-validates its own finding: the most frequent drop stack (276 occurrences, through `tcp_v4_rcv()`) lines up closely with `nstat`'s own `TcpPassiveOpens`/`TcpExtTCPDeferAcceptDrop` counters (278 each) captured over the identical window — the small discrepancy explained simply as the extra time needed to actually fetch the counters — giving reasonable confidence the stack trace and the counter really are describing the same underlying event. **A concrete, practical detail worth remembering**: this tool requires `nstat` (from `iproute2`) to be installed to function at all, and — because it shells out via `system()` — must be run with bpftrace's `--unsafe` flag, and will **interfere with any other concurrent user of `nstat`** on the same system, since it resets and restores the counters as a side effect.

## 10.3.29 `skblife` — `sk_buff` lifespan, with an honestly-documented undercounting caveat

Measures how long an individual `sk_buff` object lives, from kernel slab-cache allocation to free — by kprobing the **generic** `kmem_cache_alloc()`/`kmem_cache_alloc_node()`/`kmem_cache_free()` functions and checking (via `kaddr()`) whether the specific cache involved is one of the two skb-related caches (`skbuff_fclone_cache`, `skbuff_head_cache`). A production example shows most `sk_buff`s living 16–64 μs, with outliers stretching to the 128–256 **millisecond** range — flagged as worth cross-referencing against this chapter's other queue-latency tools to localize where that extra time is actually going. **Two caveats the book states directly and explicitly, worth taking as seriously as the tool's actual output**: first, because GSO/GRO/TCP coalescing (`tcp_try_coalesce()`) can split one packet into several `sk_buff`s or merge several into one, **the true lifespan of a full logical packet can be undercounted** by measuring individual `sk_buff` objects in isolation — the book explicitly names this as a real limitation the tool doesn't currently correct for, rather than glossing over it. Second, because it kprobes the *generic* slab-allocator functions (used for far more than just networking) rather than something skb-specific, overhead can become significant on busy systems — explicitly recommended for **short-term analysis only**, with a forward-looking note that a dedicated skb-allocation tracepoint (to pair with the already-existing `skb:consume_skb`/`skb:free_skb`) would let a future version narrow this considerably.

## 10.3.30 `ieee80211scan` — WiFi scan tracing, with a genuinely charming personal origin story

Traces IEEE 802.11 (WiFi) network scanning — the process a device goes through checking channels/frequencies for available access points — printing scan start, each channel checked (with whether a beacon was found), and total scan duration; a real example shows a `wpa_supplicant`-initiated scan taking **3,205 ms**. **The tool's own footnoted origin is worth remembering as a nice, human illustration of "scratch your own itch" tool-building**: the author traces his interest in this exact problem back to being stuck in a hotel room in 2004 with a laptop that wouldn't connect to WiFi and no diagnostic information explaining why, prompting an ad hoc DTrace-based scan tracer at the time — this bpftrace version is a direct spiritual descendant, built specifically for this book. **A real, stated limitation in the source worth flagging**: it uses one single global `@start` timestamp rather than a keyed map, so it explicitly assumes only **one scan runs at a time** — a tool built for genuine parallel-scan tracking would need a proper per-scan key, exactly the kind of design decision this book has flagged repeatedly (Chapter 9's `biolatency`, this chapter's own `superping`) as important to get right whenever concurrent instances of the same event type are possible.

## 10.3.31 Other tools worth knowing exist

`solisten(8)` (BCC — contributed by Jean-Tiare Le Bigot, one of the relatively few tools in this book credited to an outside contributor rather than the book's own author) — socket `listen(2)` call details. `tcpstates(8)` (BCC) — a line of output for **every** TCP state transition (not just aggregate lifespan like `tcplife`), with address/port/duration-in-state, built on the same `sock:inet_sock_set_state` tracepoint used elsewhere in this chapter. `tcpdrop(8)` (BCC and bpftrace) — address/state/kernel-stack details specifically for packets dropped via the kernel's `tcp_drop()` function (the TCP-specific sibling of this chapter's more general `skbdrop(8)`). `sofdsnoop(8)` (BCC) — traces file descriptors passed between processes over Unix domain sockets. Plus three tools from **earlier** chapters explicitly called back to as directly relevant here: `profile(8)` (Ch. 6 — CPU stack sampling can quantify time spent specifically in network code paths), `hardirqs(8)`/`softirqs(8)` (Ch. 6 — measuring time in networking hard/soft interrupts specifically), and `filetype(8)` (Ch. 8 — already shown identifying socket reads/writes via inode type).

## 10.4 BPF One-Liners — including a genuinely instructive worked example

A representative sample (both BCC and bpftrace given side by side where the book provides both):

```
# BCC: count failed connect(2)s by error code
argdist -C 't:syscalls:sys_exit_connect():int:args->ret:args->ret<0'

# bpftrace: same, with the error code negated to a positive errno for readability
bpftrace -e 't:syscalls:sys_exit_connect /args->ret < 0/ { @[comm, - args->ret] = count(); }'

# BCC / bpftrace: TCP send size histogram
argdist -H 'p::tcp_sendmsg(void *sk, void *msg, int size):int:size'
bpftrace -e 'k:tcp_sendmsg { @send_bytes = hist(arg2); }'

# bpftrace: count TCP retransmits by type and remote host
bpftrace -e 't:tcp:tcp_retransmit_* { @[probe, ntop(2, args->saddr)] = count(); }'

# bpftrace: receive-side CPU balance, per network device
bpftrace -e 't:net:netif_receive_skb { @[str(args->name)] = lhist(cpu, 0, 128, 1); }'
```

**A footnote attached to the socket-send/receive one-liners is worth promoting to a standing rule, since it's the single clearest, most repeatable statement of this chapter's central caveat**: syscall-level tracing (like Part 1's `soconnect`) runs in reliable process context, so `pid`/`comm` there are trustworthy; kprobes deeper in the kernel (like `sock_sendmsg`/`tcp_sendmsg`) may run with a *different* process on-CPU than the one that actually owns the connection — these usually still work correctly in practice, but "usually" is doing real work in that sentence, and it's worth remembering as the reason so many tools in Parts 2–3 describe their own PID attribution as merely "best effort."

**The one-liners examples subsection walks a full `t:net:net_dev_xmit { @[kstack] = count(); }` capture that's worth understanding as a complete worked reading exercise in itself**: one of the two captured stacks shows a clean, expected path — a `write(2)` syscall descending through VFS, sockets, TCP, IP, and the net device layer down to the driver. **The second stack is more interesting, and directly demonstrates Chapter 2's inlining warning one more time, very concretely**: it shows the CPU idle thread receiving a hardware interrupt, running the NAPI receive path, reaching `tcp_rcv_established()`, and then jumping straight to `__tcp_push_pending_frames()` with **no visible frames in between** — even though the real call chain is `tcp_rcv_established()` → `tcp_data_snd_check()` → `tcp_push_pending_frames()` → `__tcp_push_pending_frames()`. The two missing middle functions were small enough that the compiler **inlined them away entirely**, so they simply never appear as distinct stack frames — the underlying logical event this stack is capturing (TCP opportunistically checking for pending transmits while it's already busy handling an incoming packet) is real and correctly identified, but the *visible* stack doesn't literally match the *source-level* call graph, exactly as Chapter 2 warned it might.

## 10.5 Optional exercises worth trying

Write `solife(8)`, a socket-layer lifespan tool paralleling `tcplife(8)` but built from `connect()`/`accept()` to `close()` on the file descriptor; extend `tcpwin.bt` with dedicated "retrans" and "new-connection" event types, feeding richer data into the same CSV/R plotting workflow already demonstrated; modify `tcplife(8)` to emit **DOT format** output for graph visualization (e.g., with GraphViz) — turning connection relationships into an actual visual graph rather than a table; and — flagged explicitly as advanced and **unsolved even by the book's own author** — build a tool measuring true TCP round-trip time (RTT) per remote host directly (either by timing sequence numbers against their ACKs, or by reading `struct tcp_sock`'s own `rtt_min` field), a full `sk_buff`-lifespan tool that correctly accounts for GRO/GSO/coalescing (explicitly acknowledged as "much more complex than `skblife(8)`"), and separate tools for TCP pacing latency and byte-queue-limit latency specifically.

## 10.6 Summary

This was the largest chapter in the book, and its 31 tools trace every layer between an application and a NIC: sockets (Part 1), TCP (Part 2), and UDP, DNS resolution, IP/ICMP, qdiscs, and network devices (this file). **Three ideas are worth carrying forward as this chapter's real, durable takeaways, since they'll keep applying to any future networking investigation you do beyond this book's specific tool catalog**: first, **trace the low-frequency proxy event instead of the high-frequency raw event** wherever one exists (retransmits instead of all packets, new sessions instead of every packet in them) — this chapter's overhead numbers were consistently the most extreme in the book, making this discipline more important here than almost anywhere else. Second, **process attribution gets progressively less reliable the deeper into the stack you trace** — syscall-level tools (Part 1) are trustworthy; TCP/IP-level kprobes (Parts 2–3) are "best effort," and several tools in this chapter show their own working solutions for coping with that (caching context early, at the one or two states where it's still valid, rather than trusting it everywhere). Third, **`tcpsnoop`'s cautionary tale (Part 2) is this whole chapter's design philosophy in one story**: fewer kprobes, fewer struct-field dependencies, and tracepoints wherever they exist — not because it's always possible, but because the alternative (an ambitious tool that breaks on 7 of the next 12 kernel releases) is a genuinely worse outcome than a slightly less complete tool that keeps working.

## Quick-reference glossary (Chapter 10 terms, Parts 1–3)

- **Best-effort PID/COMM attribution** — the recurring caveat for any tool tracing below the syscall layer, since TCP/IP events don't always run in the originating process's own context.
- **SYN backlog / listen backlog** — the two queues a passive TCP connection passes through before `accept()`; either can drop under load, with different real-world causes and fixes.
- **GSO/TSO/GRO** — software (GSO) vs. hardware-offloaded (TSO) transmit segmentation, and its receive-side complement (GRO); `netsize(8)` measures the effect of these directly.
- **Bufferbloat** — excess queueing latency from oversized buffers; several mechanisms (BQL, TSQ, pacing, EDT) exist specifically to counter it.
- **`Qdisc_ops`** — the shared enqueue/dequeue function-pointer interface every Linux qdisc scheduler implements, which is exactly why one `qdisc-fq.bt` script generalizes to six different schedulers via simple function-name substitution.

4. The general principle this book's own tools follow in response is to deliberately minimize kprobe count and struct-field reliance, and prefer tracepoints, even at some cost to how much detail a tool can capture.

Testing might not reveal this because, on a lightly loaded or simply-structured test system, the "usual" case (the calling process genuinely is still on-CPU) may hold true every time — the mismatch tends to surface specifically under real, busier, more concurrent production conditions, exactly the situations testing often doesn't fully reproduce.
