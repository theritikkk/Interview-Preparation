# ANALYSIS — what's real, what's simplified, and a defect found along the way

## The honest boundary

Everything **upstream of the exporter** is the genuine OpenTelemetry C++ SDK,
built from the actual upstream source, doing exactly what it does in
production:

- A real `TracerProvider` / `Tracer` / `Span` object graph
  (`opentelemetry::sdk::trace::TracerProviderFactory`, not a stand-in).
- Real `SpanContext`s — 128-bit trace IDs, 64-bit span IDs, generated by the
  SDK's own ID generator, not anything hand-rolled for this project.
- The real W3C Trace Context propagator
  (`opentelemetry::trace::propagation::HttpTraceContext`), doing genuine
  `Inject`/`Extract` against the actual `traceparent` header format
  (`version-traceid-spanid-flags`), not a custom header scheme.
- A real `TextMapCarrier` implementation (`HttplibHeaderCarrier`) — the one
  piece of integration glue this project *does* write, because the SDK
  can't know about Papy's specific HTTP library's header type.

**Only the exporter is simplified**: spans go to `OStreamSpanExporter`
(structured text to a file or stdout) instead of `OtlpHttpExporter` /
`OtlpGrpcExporter` talking to a real collector (Jaeger, Tempo, the OTel
Collector). That's a config-time choice, not a design compromise baked into
how the code is instrumented — see "Why not a real collector?" below.

## How to verify the tracing is really distributed, not just nested

The whole point of this project over, say, adding `std::source_location` to
Papy's logs is that a trace can span multiple *processes*. The proof is in
`scripts/demo.sh`'s output: two completely separate binaries (`papy` and
`target_server`), each running `otelTracing::init()` with its own
`TracerProvider`, each writing to its own log file, end up with spans that
share one `trace_id` — and the server's root span has a `parent_span_id`
that's exactly the client's `HTTPRequest` span's `span_id`:

```
# papy (client), from threadWorks.cpp
{ name: LoadTestRequest   span_id: e5d1ae93...  parent_span_id: 0000000000000000 }
{ name: HTTPRequest       span_id: 52336...     parent_span_id: e5d1ae93... }

# target_server, a different process entirely
{ name: HandleRequest     span_id: b40a20...    parent_span_id: 52336...     }  <- matches!
{ name: ProcessPayload    span_id: 089ba9...    parent_span_id: b40a20...    }
```

`HandleRequest`'s parent is the client's `HTTPRequest` span, read off the
wire via the `traceparent` header `target_server` never generated itself.
That linkage is only possible if the header actually left one process and
was actually parsed by the other — which is what `trace.continued_from_client`
on the server span records (`SpanContext::IsValid()` on whatever was
extracted; it's `false`, and the server spans become roots instead, if you
curl `target_server` directly with no `traceparent` header at all).

## Why not a real collector?

Same investigation discipline as Project 2: test what's actually available
before assuming it isn't, rather than defaulting to a hand-rolled fallback.

- **apt**: every Ubuntu mirror 403s. No system gRPC/protobuf/curl packages.
- **pip**: works for pure-Python packages, but there's no `grpcio` wheel for
  this platform, and `opentelemetry-exporter-otlp` needs it.
- **npm**: 403s on everything (confirmed with trivial packages like
  `lodash`, not just unusual ones).
- **GitHub (clone/release downloads)**: reachable — this is what made the
  whole project possible at all (see below).

`opentelemetry-cpp`'s OTLP exporters need either gRPC (for `OtlpGrpcExporter`)
or libcurl (for `OtlpHttpExporter`) — both unavailable here, and building
either from source on a 2-core box within a reasonable time was judged not
worth it (the same call made for the C++ gRPC path in Project 2). So the
SDK was configured with every network exporter off
(`OTELCPP_WITH_OTLP_GRPC=OFF`, `OTELCPP_WITH_OTLP_HTTP=OFF`,
`OTELCPP_WITH_OTLP_FILE=OFF`, plus Zipkin/Prometheus/Elasticsearch/
OpenTracing-bridge all off) and only `OStreamSpanExporter` was built.

This is a one-line swap in `otelTracing.cpp`'s `init()`, not a rewrite: the
exporter is constructed once, in one place, behind the same
`std::unique_ptr<trace_sdk::SpanExporter>` interface every exporter
implements. Nothing in `threadWorks.cpp`, `apiClient.*`, or
`target_server.cpp` — the actual instrumentation — would change. That's the
entire value proposition of coding against the OTel API rather than
printf-style logging: the export destination is a deployment detail.

### A build that doesn't work (and why skipping it is fine)

One upstream CMake target, `opentelemetry_configuration_core`, fails to
compile on this toolchain (GCC 13, `-std=c++23`,
`OTELCPP_WITH_STL=CXX23`) with a real incompatibility, not a flag mistake:

```
sdk/include/opentelemetry/sdk/common/custom_hash_equality.h:152:
  map.find(key)   // key is nostd::string_view
  // std::unordered_map<std::string,...>::find() only accepts
  // const std::string&, and this libstdc++ doesn't do heterogeneous
  // lookup here the way the code assumes.
```

That target only supports the YAML-file-based *declarative* SDK
configuration (an alternative to writing `otelTracing.cpp` by hand). This
project doesn't use it — `otelTracing.cpp` builds the `TracerProvider`
programmatically via factories, which has zero dependency on that code
path. `scripts/setup_otel.sh` builds the 6 targets this project actually
needs directly, by name, rather than `--target all`, which sidesteps the
broken target entirely rather than patching around it.

## Design notes on the instrumentation

**Span shape**, one per Papy request (`threadWorks.cpp::sendRequest`):

```
LoadTestRequest (root)
├── GeneratePayload        (only for lol/ocean/payload.json/file payloads)
└── HTTPRequest            (injects traceparent, calls the server)
```

`LoadTestRequest` carries `thread.id` and `payload.kind` — useful for seeing
which of Papy's worker threads produced which trace when running with
`--threads > 1`, since thread IDs aren't otherwise visible in Papy's own
console output. `HTTPRequest` is a separate child span, not folded into the
root, specifically so its duration isolates network+server time from
payload-generation time — the two are easy to conflate if request handling
is one flat span, and they have very different causes when one is slow.

**Why `SimpleSpanProcessor`, not `BatchSpanProcessor`**: `BatchSpanProcessor`
is the production default — it buffers spans and flushes them periodically
on a background thread, which is far cheaper per span. But Papy is a
short-lived CLI process (a load test that runs for N requests and exits),
and a batch processor risks losing the tail of spans if the process exits
before the next scheduled flush. `SimpleSpanProcessor` exports synchronously
the instant each span ends — slower per-span, correct for a process whose
whole run might be a handful of requests.

**Error handling**: a span's `StatusCode` is set to `kError` with a
description on both the client side (a failed/non-200 HTTP response, a
missing or malformed payload file) and the server side would be, too, if it
had a failure path to report (it's a fixed demo target — it has none). The
missing-payload-file path was run deliberately (see Verification below): it
produces an `Error`-status `GeneratePayload` span and an `Error`-status
`LoadTestRequest` root span, both fully flushed, before Papy calls
`std::exit(EXIT_FAILURE)` — confirming span export survives the abrupt-exit
path, not just the clean one.

**Why `server/` duplicates `otelTracing.*` and `httpPropagation.hpp` instead
of `#include`-ing Papy's copies**: this demo is explicitly standing in for
a *different service*, is a separate OS process and a separate binary, and
in any real deployment would be a different codebase entirely, maintained by
a different team, that simply happens to also link the OTel SDK and agree on
the W3C header format. Sharing a source file between "Papy" and "the thing
Papy talks to" would misrepresent what's being demonstrated. The actual
shared surface between them is the OTel *API* (header-only, stable) and the
wire format (`traceparent`) — not source code — which is the realistic
version of how two independently-deployed, OTel-instrumented services relate
to each other.

## A pre-existing Papy build defect found along the way

Getting Papy to build **at all** on this Linux sandbox — before any
OpenTelemetry code was added — surfaced a real, pre-existing bug in Papy's
own repository, unrelated to tracing:

Papy vendors OpenSSL and zlib as prebuilt shared libraries rather than
depending on the system package manager (`src/dependencies/openssl/`,
`src/dependencies/gzip/`). The Makefile's non-macOS branch pointed its
linker search path at `$(OPENSSL_DIR)/lib` and `$(ZLIB_DIR)/lib` — but the
actual `.so` files ship inside `include/`, not `lib/` (confirmed with
`find`: only an `include/` directory exists under either vendored
dependency). Only the macOS branch (pointing at Homebrew's install
locations) had apparently ever been exercised; the Linux vendored-library
path looks like it was never actually linked against before. **Fix**:
point `OPENSSL_LIBDIR`/`ZLIB_LIBDIR` at `include/` on non-macOS, matching
where the files actually are.

That alone was enough to link, but not enough to be *correct*: the vendored
`.so` files have embedded `SONAME`s (`libssl.so.3`, `libcrypto.so.3`,
`libz.so.1` — checked via `objdump -p`), but the vendored directory only
contains files named `libssl.so`/`libcrypto.so`/`libz.so` (no version
suffix). At link time that's fine (the linker resolves `-lssl` by filename),
but at **runtime** the dynamic loader searches for the file named after the
embedded SONAME — which doesn't exist in the vendored directory — so it
silently falls through to the system's OpenSSL/zlib instead, if one happens
to be installed. In this sandbox one is, so the binary ran either way, but
that defeats the entire point of vendoring: on a machine without system
OpenSSL 3.x, the binary would fail to start. Confirmed with `ldd` before and
after: before the fix, `libssl.so.3 => /lib/x86_64-linux-gnu/libssl.so.3`
(system copy); after adding SONAME-named copies alongside the originals in
the vendored directories, `libssl.so.3 =>
.../dependencies/openssl/include/libssl.so.3` (the vendored one, as
intended).

Both fixes are confined to the Makefile and the vendored dependency
directories — no Papy application code was touched by this, and it would
have needed doing even without any OpenTelemetry work.

## What was actually verified

Everything below was *run*, not just written — matching the standard set by
Projects 1 and 2:

- **Full integrated build**: `make -C papy-src/Papy-main` compiles all 11
  translation units and links cleanly against the real OTel static
  libraries (previously only `otelTracing.cpp` had been compile-tested in
  isolation; the full build surfaced zero additional errors).
- **Single-request trace match**, run 5 times back to back: every run
  produces a fresh, distinct `trace_id`, and the client and server logs
  agree on it every time (`scripts/demo.sh`'s own pass/fail check, verified
  manually too).
- **Concurrency**: `--threads 4 --count 20` (80 requests total — Papy's
  `--count` is per-thread, not a global total, which is a pre-existing
  Papy CLI semantic, not something introduced here) against `target_server`
  produced exactly 80 `HTTPRequest` spans client-side, exactly 80
  `HandleRequest` spans server-side, and 80 distinct shared `trace_id`s
  between the two logs — confirmed by taking the set intersection of
  trace IDs from both log files, not just comparing counts.
- **All five payload code paths**: `--payload` unset (GET), `lol`, `ocean`,
  `payload.json`, and an arbitrary file path (`custom_payload.json`) — each
  produces a correctly-shaped `GeneratePayload` child span (skipped for the
  bare-GET path, as it should be) and a successful round trip to
  `target_server`.
- **The error path**: a `--payload` pointing at a nonexistent file produces
  an `Error`-status `GeneratePayload` span (with the parse-failure
  description attached) and an `Error`-status `LoadTestRequest` root span,
  both fully flushed to the trace log, before the process exits with
  `EXIT_FAILURE` — exercising the `std::exit()` path, not just the normal
  `return 0` path, for span-flush correctness.
- **The delivered package specifically**: after assembling the final
  `03-otel-tracing/` directory (stripped of build artifacts and the
  scratch `opentelemetry-cpp` clone used to produce `third_party/otel-cpp`),
  it was copied to a clean directory and built from scratch there — `make`
  in both `papy-src/Papy-main` and `server`, then `scripts/demo.sh` — to
  confirm the zip you're looking at is actually self-contained and doesn't
  secretly depend on files outside it.

One verification wrinkle worth naming honestly: an early concurrency test
run showed implausible results (a stress test reporting far fewer
server-side spans than client-side successes). That turned out to be a
stray `target_server` process left over from an earlier manual test,
still bound to the same port and silently absorbing traffic while a
freshly-launched instance failed to bind and exited immediately — not a
bug in the tracing or HTTP code. `scripts/demo.sh` uses `mktemp` for every
log file and a `trap`-based cleanup specifically so this class of mistake
can't happen when you run it yourself.
