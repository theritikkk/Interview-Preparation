# FleetTelemetry — a gRPC-shaped service, built on real Protocol Buffers

A small "fleet telemetry" service demonstrating all four gRPC RPC
patterns — unary, server streaming, client streaming, and bidirectional
streaming — with **real Protocol Buffers** as the message format: a real
`.proto` schema, compiled by the real `protoc` compiler, into real
generated message classes, serialized with the real `protobuf` runtime.

The one thing that's hand-rolled is the transport that carries those
messages between processes, standing in for gRPC's own HTTP/2-based
transport. **Why**, exactly, and what that trade-off costs, is in
[ANALYSIS.md](ANALYSIS.md) — this isn't a shortcut taken quietly.

## What's here

```
proto/
  telemetry.proto     the real .proto schema — messages + service definition
gen/
  telemetry_pb2.py     generated by protoc — DO NOT hand-edit, see scripts/gen.sh
rpc/
  framing.py           length-prefixed TCP framing (the hand-rolled transport)
  rpc_base.py           the four call shapes + server-side dispatcher
server.py              FleetTelemetry service implementation
client.py              exercises all four RPCs against the server
scripts/
  gen.sh               regenerates gen/telemetry_pb2.py from the .proto file
  demo.sh              starts the server, runs the client, checks the result
```

## The service

```protobuf
service FleetTelemetry {
  rpc RegisterDevice(DeviceInfo) returns (RegisterAck);        // unary
  rpc StreamAlerts(DeviceId) returns (stream Alert);            // server streaming
  rpc UploadReadings(stream SensorReading) returns (ReadingsSummary); // client streaming
  rpc ControlChannel(stream Command) returns (stream Status);   // bidirectional streaming
}
```

A small IoT-fleet theme was picked specifically because it needs all four
shapes naturally: register a device once (unary), subscribe to a stream
of alerts pushed from the server (server streaming), batch-upload a
sensor log and get one summary back (client streaming), and hold an
open, two-way command/status channel (bidirectional streaming).

## Setup

You need `protoc` (the Protocol Buffers compiler) and Python 3 with the
`protobuf` package. If `protoc` isn't already on your machine:

```
# Debian/Ubuntu
apt-get install -y protobuf-compiler

# macOS
brew install protobuf

# Any platform — a prebuilt binary release
# https://github.com/protocolbuffers/protobuf/releases
```

```
pip install protobuf
bash scripts/gen.sh      # generates gen/telemetry_pb2.py
```

## Run the demo

```
bash scripts/demo.sh
```

Starts the server, runs the client through all four RPCs in sequence,
prints everything that happened, checks the client actually succeeded,
and shuts the server down. Prints `DEMO PASSED` or `DEMO FAILED`.

To run them separately and watch the two sides at once:

```
python3 server.py        # terminal 1
python3 client.py        # terminal 2
```

## Regenerating after a schema change

Edit `proto/telemetry.proto`, then:

```
bash scripts/gen.sh
```

This is the real `protoc` compiler doing real code generation — nothing
about the message layer is hand-maintained.
