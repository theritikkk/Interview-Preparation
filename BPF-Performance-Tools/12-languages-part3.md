# Chapter 12 — Languages (Part 3 of 3: Bash, Other Languages, Summary)

*Study notes on Chapter 12 of BPF Performance Tools (Brendan Gregg, 2019). Original notes, not book text — see `00-index.md` for how these notes are written. Continues directly from Parts 1–2 (background taxonomy, C, and Java).*

## 12.4 Bash Shell — a live, first-time debugging session, worked in full

**Framing worth keeping in mind for this whole section**: interpreted languages are rarely performance-critical targets in their own right (performance-sensitive workloads usually get written in something faster) — so BPF tracing here is more often for **troubleshooting and understanding behavior** than for chasing microseconds. The book is explicit that this section's real purpose is methodological: *"This section will show how I approach an unknown interpreted language and determine how to trace it for the first time: an approach that you can follow for other languages."* It delivers on that promise unusually honestly — including a real dead end, documented as a dead end rather than edited out.

### Setup

`ldd /bin/bash` reveals bash's shared-library dependencies (`libtinfo`, `libdl`, `libc`, the dynamic linker) — a reminder that, exactly as flagged already for `readline()` back in Chapters 5, 11, and §12.2.3, bash's real implementation can be split across the main binary and these libraries depending on the distribution. **The book builds its own copy of bash specifically with `CFLAGS=-fno-omit-frame-pointer ./configure && make`** — giving it both working frame-pointer stack walks *and* a local, unstripped symbol table (unlike the default `/bin/bash`), deliberately setting up the "easy" starting conditions for what follows, with the harder, stock-binary case saved for §12.4.4.

**A small, deliberately-instrumented test program, `welcome.sh`, is the whole section's ground truth**: a `welcome` function called seven times, each call echoing three lines — 21 total `echo` calls, numbers chosen specifically to "stand out" against other background activity while tracing.

### 12.4.1 Function counts — guessing, then confirming, with real numbers

Starting from nothing but a hunch, `funccount 'p:/home/.../bash:*func*'` wildcard-matches every function with "func" in its name — and the result **directly confirms the hunch**: `execute_function()` was called exactly **seven** times, matching the known workload precisely. Following the naming pattern further, `funccount 'p:/home/.../bash:execute_*'` finds `execute_builtin()` called **21** times (exactly matching the known `echo` count) and `execute_command()` called **23** times (plausibly the 21 echoes plus the function declaration plus the final `sleep`) — each number checked directly against the known ground truth before being trusted, exactly the validation discipline Part 1's strategy section (§12.1.5, step 5) recommended in the abstract, now shown actually happening.

### 12.4.2 `bashfunc.bt` — reading real kernel/application source to find the right struct field

To find out *which* function is being called (not just that a call happened), the book reads `execute_function()`'s actual signature directly from bash's own C source (`execute_cmd.c`), finding its first argument is a `SHELL_VAR *` — a real struct (`struct variable` in `variables.h`) whose first member, `name`, is a plain `char *`. **Two working versions are shown side by side, illustrating a real, meaningful tradeoff**: one `#include`s the real header directly (works, but throws a harmless-but-visible warning about a second, unrelated missing header, `stdc.h`, and creates a build-time dependency on having that exact header available); the second **hand-declares only the one struct member actually needed** — a "partial struct," the same minimal-struct technique already used by Chapter 9's `runqlen(8)` — avoiding the header dependency entirely while still working correctly. **The book's own explicit caveat, worth remembering as a standing rule for any uprobe-based struct-field tracing**: *"uprobes are an unstable interface, so this program may stop working if bash changes its function names and arguments."*

### 12.4.3 `bashfunclat.bt` — validating against a *known* latency, then building the real tool

The book modifies `welcome.sh` to `sleep 0.3` inside the function — a **known, exact, controllable latency** — and first sanity-checks it with BCC's generic `funclatency(8)`, confirming the measured latency lands cleanly in the **256–511 ms** histogram bucket, exactly where a 0.3-second sleep should land. Only *after* this validation does the book build the real, purpose-specific tool: a standard entry/return timestamp-pair script (§5.7.12's idiom, now applied to a shell interpreter instead of a kernel function), caching both the function's **name** and its **start time** in maps keyed by `tid`, and computing a per-function-name histogram on return. This is worth remembering as a clean, complete, real demonstration of the "validate against a known workload before trusting a new tool" discipline (Part 1's strategy step 5, and echoed from Chapter 9's disk-tooling advice) — not just stated as good practice, but actually followed, in order, with a real number to check against.

### 12.4.4 `/bin/bash` — the real, honest debugging adventure

**This is the single best "watch an expert actually work through a dead end" narrative in the entire book, and it's worth reading in full rather than summarized to just the ending.** The book's own framing sets it up directly: *"Up until now, tracing bash has been so straightforward that I started worrying it wasn't representative of the gritty debugging adventures one normally encounters when tracing interpreters."* Switching every tool built so far from the custom-built bash over to the stock, default `/bin/bash` — **everything breaks immediately**. `execute_function()` no longer appears in `funccount`'s output at all.

**The root cause, confirmed directly rather than assumed**: `readelf --syms --dyn-syms` shows `execute_function()` exists in the custom build as a symbol of binding type **`LOCAL`**, while `restore_funcarray_state()` (still visible in `/bin/bash`) is bound **`GLOBAL`** — and `strip(1)`, exactly as explained back in §12.2.1, removes local symbols specifically, which is precisely why one function survived stripping and the other didn't.

**The recovery path, shown as genuine, sequential problem-solving rather than a known-answer-in-advance walkthrough:**
1. Since `restore_funcarray_state()`'s call count (7) still matched the known workload, the book tries `stackcount -P` on it directly against stock `/bin/bash` — producing a **completely broken** `[unknown]` / `[unknown]` stack, a direct, concrete illustration of *why* the custom frame-pointer-preserving build was worth making in the first place.
2. Running the *identical* `stackcount` against the **custom-built** bash's version of the same function instead produces a full, clean, readable call chain — `restore_funcarray_state` ← `without_interrupts` ← `run_unwind_frame` ← `execute_function` ← ... ← `main` — **confirming**, now with real evidence rather than a guess, that `restore_funcarray_state()` genuinely is a child of the now-unreachable `execute_function()`.
3. Hoping the actual function *name* might be reachable through `restore_funcarray_state()`'s own argument (`struct func_array_state`, read directly from source), the book declares the relevant struct fields and tries to print them — **and this doesn't work**. The book states this plainly, as a real dead end: *"I was unable to find the function name."*
4. **Rather than treating that as a stopping point, the book lists real, concrete next options** — worth internalizing as a general "what do I try when my first idea doesn't pan out" checklist: check whether *other* interesting-sounding functions `funccount` already flagged (`find_function()`, `make_funcname_visible()`, `find_function_def()`) might carry the name in *their* arguments instead, cacheable for later lookup; or check whether any of the higher-level functions visible in the broken stack (`execute_command()`) are *themselves* still present as global, unstripped symbols and usable as an alternate instrumentation point.
5. **The first alternative worked immediately**: `find_function_def()` turned out to take the function name directly as its first argument, and — crucially — is **still a global, unstripped symbol** even in `/bin/bash`. The final, working tool traces two *different* functions together: `find_function_def()` (to capture and cache the name, keyed by `tid`) and `restore_funcarray_state()` (as the trigger to print it and clean up) — neither one being the function the book originally, ideally wanted to instrument (`execute_function()`), but together giving the same practical result.

**The book's own closing caveat for this whole exercise is worth remembering precisely, since it generalizes the entire section's lesson into one sentence**: *"While this works, this is tied to this version of bash and its implementation."* Working around a stripped symbol by chaining two unrelated, still-visible functions together is a genuinely valuable technique — but it's explicitly more fragile, not less, than the original (already-unstable) approach, because it now depends on the *specific relationship* between two internal functions holding true, not just one function's continued existence.

### 12.4.5 `/bin/bash` USDT — what a "done right" version would look like

The book's own proposed hypothetical probe design — `bash:execute__function__entry(char *name, char **args, char *file, int linenum)` and a matching `__return` probe — would make everything in §12.4.2–12.4.4 trivial and *stable* across bash versions, at the cost of someone actually adding it to bash's source. As concrete prior art, the book presents the **real** USDT probe set added to the Solaris **Bourne shell (`sh`)** — a genuinely rich set worth skimming as a template for "what would a *thoroughly* instrumented shell interpreter's probe set actually look like": `function-entry`/`function-return`, `builtin-entry`/`builtin-return`, `command-entry`/`command-return`, `script-start`/`script-done`, `subshell-entry`/`subshell-return`, `line` (per source line executed), and even `variable-set`/`variable-unset`. Offered explicitly as inspiration for what bash's own USDT probes could eventually look like, not as something currently available.

## 12.4.6 bash One-Liners

```
# BCC: count execution-related function calls (requires unstripped symbols)
funccount '/bin/bash:execute_*'

# BCC: trace interactively typed commands via readline()'s return value
trace 'r:/bin/bash:readline "%s", retval'

# bpftrace: same two, respectively
bpftrace -e 'uprobe:/bin/bash:execute_* { @[probe] = count(); }'
bpftrace -e 'ur:/bin/bash:readline { printf("read: %s\n", str(retval)); }'
```

## 12.5 Other Languages — brief field notes on three more runtimes

The book's own recommended process for any language not covered in depth here: identify its execution model first (§12.1's taxonomy), then study whichever of C/Java/Bash's sections matches most closely for a head start on the likely challenges, and check the book's own companion website for newer, language-specific articles as the space evolves. Three languages get brief, concrete notes:

### 12.5.1 JavaScript (Node.js)

Runs on **V8** (Google's engine, also used in Chrome) — which, like the JVM, both interprets and JIT-compiles, and manages its own memory with garbage collection — so the overall challenge profile closely mirrors Java's.

**USDT**: built-in probes exist (`gc__start`/`gc__done`, `http__server__request`/`response`, `net__server__connection`, and more — notably, a heavier emphasis on **HTTP/network** events than Java's more VM-internals-focused probe set) plus a `node-usdt` library for adding your own dynamic probes — but, exactly like Java, **not enabled by default**; Node.js must be rebuilt from source with `--with-dtrace`.

**Symbols — a genuinely important operational difference from Java's model, worth remembering specifically**: Java's `perf-map-agent`/`jmaps` approach takes a **snapshot** at a point in time. Node.js (v10+) instead offers `--perf_basic_prof`/`--perf_basic_prof_only_functions`, which write a **continuously-updated, rolling log** instead — and the book flags a real, concrete operational gotcha: **this rolling log cannot be disabled while the process is running**, so over a long-lived process's lifetime it can grow to **gigabytes**, mostly stale entries. The book's actually-recommended approach instead is the **`linux-perf` module**, which combines the rolling-write behavior with Java-`perf-map-agent`-style full-heap capture, letting you start capturing fresh symbols at any point in a running process's life. **A real, counterintuitive bug worth remembering explicitly, footnoted directly in the book**: you might reasonably assume tools reading these logs would prefer the *most recent* mapping for a given address — the book found this assumption **false**, with older mappings sometimes incorrectly winning over newer ones — requiring manual post-processing of the log (keeping only each address's newest entry) before trusting it. A separate, useful flag, `--interpreted-frames-native-stack` (also v10+), lets *interpreted* (not-yet-JIT'd) JavaScript functions show their real names in a stack trace too, instead of a generic `"Interpreter"` placeholder frame.

**Function tracing — the section's real conclusion, worth taking as the practical answer for this language**: there are **no USDT probes for individual JavaScript function calls**, and the book states plainly that V8's own architecture would make adding them "challenging" — and, if added anyway, would likely carry the same order-of-magnitude overhead penalty Java's extended probes showed (§12.3.6). **The actual, practical answer given is a direct application of Part 1's §12.1.4 point about stack traces alone often being enough**: JavaScript function names are already visible in ordinary **stack traces** collected at kernel events (timed sampling, disk I/O, TCP events, context switches) — meaning CPU flame graphs and similar stack-based analysis, once the symbol-file workflow above is in place, deliver most of the real value without ever needing true per-function tracing at all.

### 12.5.2 C++

Traces almost exactly like C (§12.2), with two real, specific differences worth knowing: **symbol names are mangled** (`ClassLoader::initialize()` becomes something like `_ZN11ClassLoader10initializeEv`) — BCC and bpftrace both demangle these automatically for display, and the book suggests **wildcard matching on a readable substring** (`uprobe:/path:*ClassLoader*initialize*`) as more practical than trying to type out a full mangled name by hand. Second, **calling conventions may not map cleanly onto simple argument numbering**: an implicit `self`/`this` object can shift argument positions by one, and strings are frequently **C++ objects**, not raw C strings — meaning they can't simply be dereferenced with `str()` the way a C `char *` can, and instead require declaring the actual object's struct layout in your BPF program to read its members correctly. The book flags **BTF** (Chapter 2) as a plausible future fix for having to hand-declare these structs at all, once it can supply argument/member locations automatically.

### 12.5.3 Golang — a real, serious safety warning worth remembering above all else in this section

Go compiles to real binaries and traces similarly to C in most respects — **but with genuinely important differences around calling conventions, goroutines, and dynamic stack management that are worth taking seriously, not just noting in passing.**

**Stack walking and symbols are, refreshingly, the easy part**: both major compilers — **Go's own `gc`** (since Go 1.7) and **`gccgo`** — honor the frame pointer **by default**, and both always include real symbols in the output binary. This means Go stack traces from kernel *or* user-level events, and CPU profiling via timed sampling, should simply work immediately, with none of the recompilation/`jmaps`-style workarounds Java and Node.js both needed.

**Function-entry tracing works via ordinary uprobes for both compilers**, though naming conventions and binary layout differ: `gc`-compiled binaries are statically linked, with functions directly traceable in the main binary (`fmt.Println`, `fmt.newPrinter`, ...); `gccgo`-compiled binaries are **dynamically linked**, with the same functions living in a separate `libgo.so` that needs to be the actual uprobe target instead.

**Function *arguments* genuinely differ by compiler, in a way worth understanding precisely**: `gccgo` uses the **standard AMD64 ABI**, so bpftrace's ordinary `arg0`/`arg1`/... built-ins work exactly as they would for C. **Go's own `gc` compiler instead uses a Plan 9-derived, stack-passing calling convention** — arguments aren't in registers at all, and must be read directly off the stack via `reg("sp")` plus a manual byte offset (the book's own live example: `*(reg("sp") + 8)` and `*(reg("sp") + 16)` to read a two-int-argument `add(x, y)` call) — with a forward-looking note that a future bpftrace version might add friendlier aliases (`sarg0`, `sarg1`) for exactly this pattern. **A real, easy-to-hit practical gotcha attached to both examples**: the target function needs to be compiled with **inlining explicitly disabled** (`gccgo -O0`, or `go build -gcflags '-N -l'`) — otherwise the small `add()` function in the book's own demo would simply be inlined away and never exist as a separately traceable unit at all, directly echoing Chapter 2's inlining warning yet again, this time as something you have to proactively defeat at compile time just to have anything to trace.

**The single most important, safety-critical point in this entire section, worth remembering above every other detail here**: **`uretprobes` are currently unsafe to use on Go `gc` binaries, and can genuinely crash the target program or corrupt its data.** The precise mechanism, worth understanding rather than just avoiding blindly: a `uretprobe` works by installing a trampoline handler that temporarily modifies the target function's return-address location on the stack. **The Go runtime can move or resize a goroutine's stack at any time**, with no awareness that the kernel has made this modification — so by the time the original bytes are supposed to be restored, that exact memory location may now hold **completely different, legitimate Go program data**, which the kernel will overwrite anyway, corrupting it. The book credits Gianluca Borello with an experimental workaround: **disassembling the target function ahead of time to find its actual return instruction addresses, then placing ordinary (safe) `uprobes` directly at those specific addresses**, rather than relying on the automatic-but-unsafe `uretprobe` mechanism at all. **A second, separate, real gotcha, worth connecting explicitly to a pattern you've now seen several times in this book**: goroutines can be freely **rescheduled onto different OS threads while running** — meaning the standard `@start[tid] = nsecs` latency-timing idiom, used throughout this entire book (Chapter 5's flagship example onward), **is not reliable for timing Go functions**, for exactly the same underlying reason Chapter 9's `biolatency`/`biosnoop` couldn't key on thread ID for disk I/O: the entity you're timing doesn't necessarily stay on one thread from start to finish. (The book flags this as a real, open problem here rather than supplying a ready fix — consistent with §12.1's own framing of language tracing as a genuinely evolving space.)

**USDT**: the **Salp** library extends `libstapsdt` (Chapter 2's dynamic-USDT mechanism, already covered there for Node.js and Python) to Go as well — the same general "compile a small real shared library with genuine static probes, then call into it" pattern from Chapter 2 §2.11, just with a Go-specific wrapper.

## 12.6 Summary

Whatever language you need to trace — compiled, JIT-compiled, interpreted, or some mix of all three within the same process — there is very likely a workable BPF-based approach, and this chapter's real value is the **method**, demonstrated three times over on C, Java, and Bash: identify the execution model, find or add stable instrumentation (USDT) where possible, understand exactly why stack walking and symbol resolution do or don't work, and validate every new tool against a workload with a known, controllable answer before trusting its output on anything real. Brief notes on JavaScript, C++, and Golang extend the same method to three more runtimes, each with its own specific wrinkles — culminating in Golang's genuinely serious `uretprobe` safety warning, worth remembering as proof that "this technique is unstable" and "this technique is actively unsafe" are two different severities of warning this book has now shown, and it's worth being able to tell them apart.

## Quick-reference glossary (Chapter 12, all three parts)

- **Execution model** — whether a runtime compiles ahead-of-time, JIT-compiles, or interprets; the single question this whole chapter says to answer first, for any new language.
- **Supplemental symbol file** — an externally-generated `/tmp/perf-PID.map`-style file translating JIT'd function addresses to names after the fact (safe); different from placing a uprobe directly at a JIT'd address (unsafe — Part 1's core JIT-tracing lesson).
- **`PreserveFramePointer`** — the JVM flag (contributed to OpenJDK by this book's own author) that fixes Java's default frame-pointer omission, a direct prerequisite for Java stack walking.
- **Extended USDT probes** — a JVM/Node.js pattern of gating especially high-frequency probes (method entry/exit, object allocation) behind a second, explicit opt-in flag, specifically because their overhead (demonstrated at over 10x for Java) is too high for routine use.
- **`gc` vs. `gccgo`** — Go's two compilers, differing in calling convention (Plan 9 stack-passing vs. standard AMD64 ABI) and linking (static vs. dynamic) — a real, practical fork in how you'd trace a given Go binary.
- **Partial struct declaration** — hand-declaring only the specific struct field(s) a BPF program actually needs, instead of `#include`-ing a full, possibly dependency-heavy header — used across Chapters 9 and 12 as a lightweight, portable workaround.
