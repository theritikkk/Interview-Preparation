# Cilium, Hubble, and Tetragon on Kubernetes

Real, applyable manifests and a real runbook for Cilium (eBPF CNI +
kube-proxy replacement), Hubble (its observability layer), and Tetragon
(eBPF-based runtime security/process observability) — plus something the
original roadmap didn't expect to be possible: **a real, single-node
Kubernetes v1.31 control plane, actually stood up and verified in this
sandbox**, with a real Cilium install genuinely attempted against it.

The roadmap's original plan for this project was "docs + manifests
only, no live cluster here." That turned out to be half right: a live
cluster *is* achievable (this sandbox's container runtime is far more
capable than assumed — see `ANALYSIS.md`), but Cilium specifically
still can't finish installing here, for two distinct, precisely
diagnosed reasons that have nothing to do with Kubernetes itself. The
honest result is better than either extreme: not a simulation, and not
a full green checkmark — a real cluster, a real install attempt, and
two real, independently-confirmed stopping points.

## Run it

```
cd k3s && sudo ./setup-k3s.sh          # real k8s v1.31 control plane comes up
cd ../cilium && sudo ./install-cilium.sh   # gets as far as this sandbox's
                                             # network policy allows — see
                                             # ANALYSIS.md for exactly where
                                             # and why it stops
```

On infrastructure that can reach `quay.io` (basically anywhere outside
this specific sandbox — a real cloud VM, a laptop, a CI runner), both
scripts are the complete, correct, real install sequence and will
produce a working Cilium+Hubble dataplane with the node going `Ready`.
`tetragon/install-tetragon.sh` is the equivalent for Tetragon, written
and checked against the real chart but not run end-to-end here since
this sandbox had no working `helm` binary either (see `ANALYSIS.md`).

## The short version of why this stops where it does

Two separate, real, independently-diagnosed limitations — not one vague
"no cluster here":

1. **Every container registry this project tried is blocked by this
   sandbox's egress policy** — `quay.io`, `docker.io`, `ghcr.io`,
   `registry.k8s.io` all answer `403 Forbidden` at the CONNECT level.
   Confirmed directly: `containerd`'s own real pull attempt for
   `quay.io/cilium/cilium:v1.16.5` fails with
   `failed to do request: Head "https://quay.io/v2/cilium/cilium/manifests/v1.16.5": Forbidden`.
   (GitHub itself — both git clone and release-asset downloads — is
   allowlisted, which is *how* k3s and cilium-cli got here at all.)
2. **This sandbox's cgroup hierarchy isn't delegated for nested
   container-sandbox creation.** Independently of the registry block,
   every real pod kubelet tried to actually start (not just
   Cilium's — its own `cilium-operator`, which needs no special
   privileges) failed identically:
   `OCI runtime create failed: runc create failed: unable to start
   container process: can't get final child's PID from pipe: EOF`.
   The kubelet's own log names the precise cause:
   `cpu and memory cgroup hierarchy not unified. cpu: /, memory:
   /process_api/.../claude-code-bash` — this sandbox's own process is
   cgrouped inconsistently across controllers, which breaks runc's
   ability to create a child cgroup for any pod, Cilium or otherwise.

Full detail, exact commands, and exact captured output for both are in
`ANALYSIS.md` and `evidence/`.
