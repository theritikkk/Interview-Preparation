# Lesson 32 — Generalizing to NR SSB: Where the Pipeline's Contracts Hold, and Where a Hidden Assumption Breaks

*Stage 9, continued. Project 8. Lesson 31 asked whether its stage-contract discipline would generalize. It mostly does — except for a real, specific, informative surprise: NR doesn't just retune LTE's Zadoff-Chu parameters for PSS/SSS. It uses a genuinely different sequence family, and catching that is the actual point of this lesson.*

### 1. Intuition

Going into this lesson, the natural hypothesis is "NR PSS/SSS detection is Lesson 19's Zadoff-Chu code, just retuned for a different sequence length and numerology." That hypothesis is only half right. NR's OFDM math (Lessons 1–14) and numerology scaling (Lesson 28) really are direct, parameterizable generalizations of LTE. But 3GPP specifically moved **away** from Zadoff-Chu for PSS and SSS themselves, adopting BPSK-modulated **M-sequences** instead — while Zadoff-Chu stays exactly where Lesson 30 left it, for PRACH. This is a genuinely informative kind of "generalization failure": not a numerology bug, but a wrong assumption about which mathematical family survives at all — and it's a very realistic thing to get wrong on a first attempt.

### 2. The engineering problem that forces this

Two separate questions. First, the RF-technical one: why would standards designers move away from Zadoff-Chu — which Lesson 19 proved has *mathematically perfect* zero autocorrelation — for PSS/SSS specifically? Second, the software-engineering one: Lesson 31 §4 wrote down an explicit contract for Stage A ("outputs `{sample_offset, N_ID2}`"). Does that contract survive a complete swap of the *algorithm* inside Stage A — correlating against an entirely different sequence family — or was something about ZC's specific mathematical properties silently assumed by downstream code? You only find out by actually attempting the swap, which is exactly what this lesson does.

### 3. Mathematical foundation

An **M-sequence** (maximum-length sequence) of length $N=2^n-1$ is generated by an $n$-bit linear-feedback shift register (LFSR) over $GF(2)$, then BPSK-mapped ($0\to+1$, $1\to-1$). NR PSS and SSS both use length-127 ($n=7$) M-sequence-based constructions — real-valued, BPSK-modulated, not the complex polyphase Zadoff-Chu family from Lesson 19.

**M-sequence periodic autocorrelation** (a classical, well-established result): $R(0)=N$; $R(k) = -1$ for all $k\ne0$ — a small but genuinely **nonzero** residual, unlike Zadoff-Chu's mathematically *exact* zero (Lesson 19 §5).

### 4. Formal definition

NR PSS/SSS: length-127, BPSK, LFSR-generated M-sequences. NR PRACH (Lesson 30): still Zadoff-Chu, unchanged in family from LTE — the move away from ZC is specific to PSS/SSS, not a blanket NR-wide change, and precision about exactly which channels changed matters here.

### 5. Derivation — quantifying the ZC-vs-M-sequence trade-off, and testing the software contract

**(a) The autocorrelation gap, made concrete.** For $N=127$: peak $R(0)=127$; off-peak $|R(k)|=1$ for $k\ne0$. Ratio in amplitude: $127$; in power: $127^2$; in dB: $20\log_{10}(127)\approx42.1$ dB. So an M-sequence's correlation sidelobes sit about 42 dB below the peak — extremely good, easily sufficient for reliable detection via Lesson 6's matched filter, just not the *mathematically infinite* suppression Zadoff-Chu provides. This is a real, small, deliberately accepted cost, not an oversight — BPSK/real-valued sequences bring other practical advantages (e.g., generation simplicity, different peak-to-average power characteristics) that a standards body can reasonably trade against a 42 dB (rather than infinite) sidelobe floor; the exact weighting of those trade-offs in 3GPP's actual decision isn't something to assert with false precision, but the autocorrelation cost itself is a precise, derivable fact.

**(b) Whether Lesson 31's contract survives the swap.** Stage A's contract was: given a raw IQ stream, output `{sample_offset, N_ID2}`. Internally, `detect_pss()` must now correlate against three candidate M-sequences instead of three candidate ZC sequences — a **complete** rewrite of the function body. But if Lesson 31's contract was well-designed — specifying only the *output meaning*, never depending on ZC-specific internals like "the correlation peak is mathematically exact" — then Stages B, C, and D require **zero changes**, since they only ever consumed `sample_offset` and `N_ID2` as opaque values, never anything about *how* Stage A computed them. This is a genuine, testable claim about interface design, not just an assertion: attempting the swap is the only way to find out whether it actually holds, or whether some downstream stage secretly assumed something ZC-specific that an M-sequence-based Stage A no longer provides.

### 7. Worked example

A concrete illustration of §5(a): the same peak-detection logic from Lesson 19 §9 (find the argmax of correlation magnitude) works essentially unchanged against an M-sequence's correlation output — the peak is still by far the tallest feature, at $127\times$ the amplitude of any sidelobe. The *detection* logic generalizes cleanly; only the *reference sequence generation* code (Zadoff-Chu formula vs. LFSR) needed to change.

### 8. Code

```cpp
#include <vector>
#include <cstdint>

// A 7-bit LFSR generating a length-127 maximal-length sequence
// (one standard primitive polynomial choice for GF(2^7))
std::vector<int8_t> generate_m_sequence(uint8_t seed = 0b1111111) {
    std::vector<int8_t> seq;
    uint8_t state = seed;
    for (int i = 0; i < 127; ++i) {
        int bit = state & 1;
        seq.push_back(bit ? -1 : 1);                 // BPSK map: 0->+1, 1->-1
        int feedback = ((state >> 0) ^ (state >> 6)) & 1;  // taps per a primitive polynomial
        state = (state >> 1) | (feedback << 6);
    }
    return seq;
}

// Same shape as Lesson 19's ZC autocorrelation check -- different sequence family inside
void check_autocorrelation(const std::vector<int8_t>& seq) {
    int N = seq.size();
    for (int k = 0; k < N; ++k) {
        long r = 0;
        for (int n = 0; n < N; ++n) r += seq[n] * seq[(n + k) % N];
        // expect: r == N at k=0, r == -1 for all other k (Sec 3's classical result)
        if (k < 5) printf("R(%d) = %ld\n", k, r);
    }
}

// Stage A's SIGNATURE is completely unchanged from Lesson 31 Sec 8 --
// only its internals (which sequence family it correlates against) differ.
// PssResult detect_pss_nr(const std::vector<std::complex<float>>& rx,
//                         const std::vector<std::vector<int8_t>>& nr_pss_refs) { ... }
```

### 9. Experiment

Run `check_autocorrelation` on the generated M-sequence and confirm $R(0)=127$, $R(k)=-1$ for the first several nonzero $k$ — direct numeric confirmation of §3's classical result, the same "verify the claimed math with real numbers" discipline used for Zadoff-Chu back in Lesson 19 §9. Then take your actual Lesson 31 pipeline, replace only Stage A's internals with M-sequence correlation (keeping the exact same function signature), and rerun Lesson 31 §9's end-to-end integration test unchanged — confirming whether Stages B–D genuinely required zero modification, which is the real test of §5(b)'s claim.

### 10. Expected output

$R(0)=127$ exactly; $R(k)=-1$ exactly for every nonzero $k$ tested — the classical result confirmed to the integer, not just approximately. If Lesson 31's contracts were genuinely well-designed, the full pipeline re-passes its integration test with only Stage A's body changed and nothing else touched.

### 11. Debugging exercise

Symptom, no cause given: you adapt your Lesson 31 pipeline for "NR" by simply changing the length parameter in your existing Zadoff-Chu code from 63 to 127, leaving everything else the same. The code runs and produces correlation peaks — but when checked against real spec-compliant NR PSS reference values, it never matches.

Given everything this lesson just established: why can *no* choice of length parameter within the Zadoff-Chu formula ever produce the correct answer here?

**Root cause (revealed):** this is exactly the wrong-assumption trap this lesson opened with. NR PSS isn't a longer or differently-parameterized Zadoff-Chu sequence — it's a **different sequence family entirely** (an LFSR-generated M-sequence, §3). Changing $N$ in Zadoff-Chu's formula $x_u[n]=e^{-j\pi un(n+1)/N}$ produces a different *Zadoff-Chu* sequence, full stop — no parameter choice within that formula can ever produce an M-sequence's values, because they come from fundamentally different generating mathematics (a complex exponential recurrence versus a binary linear-feedback shift register). The fix isn't retuning a parameter; it's implementing the actually-correct generating algorithm, exactly as §8 does.

### 12. Common mistakes

- Over-generalizing "NR is LTE with configurable parameters" into a universal rule — true for OFDM/numerology (Lesson 28), **false** for the PSS/SSS sequence family specifically. This lesson's whole point is that the generalization has a real, sharp boundary, and knowing exactly where it sits beats a vague, blanket assumption either way.
- Concluding NR "abandoned Zadoff-Chu" entirely — imprecise; PRACH (Lesson 30) still uses it, unchanged in family. Precision about *which specific channels* changed sequence family, and which didn't, is the actual engineering content here.
- Assuming a contract "has always worked" is strong evidence it's well-designed — Lesson 31's contract could pass every test right up until this lesson's implementation swap, at which point a genuinely leaky assumption (had one existed) would only become visible now. Passing tests so far is weak evidence of good interface design; surviving an actual implementation swap is much stronger evidence.

### 13. Real RF/cellular application

Exactly this "which assumptions are genuinely LTE/NR-shared versus technology-specific" reasoning is central to real dual-mode modem and RAN software architecture, where shared PHY infrastructure (FFT, equalization, a generic matched-filter library) coexists deliberately with technology-specific sequence-generation and control logic. Real codebases like srsRAN and OpenAirInterface make exactly this kind of shared-vs-specific architectural split, and this lesson is a small, honest, hands-on encounter with that genuine design challenge — not a simplified analogy of it.

### 14. Interview question

*"You're told 5G NR reuses much of LTE's PHY design with 'just different parameters.' Where does that claim hold, and where does it specifically break?"* A strong answer, from this lesson: it holds for the underlying OFDM/cyclic-prefix mathematics (Lessons 1–14, entirely unchanged) and for genuinely parameterizable structural choices like numerology (Lesson 28); it breaks specifically for the PSS/SSS sequence family, which moved from Zadoff-Chu to M-sequences, while PRACH retained Zadoff-Chu in both generations. Demonstrating you know exactly where the analogy holds and where it doesn't is a stronger signal than either extreme — "identical" or "completely different" are both wrong.
