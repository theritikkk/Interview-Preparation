# Distributed Systems Practice — Roadmap

This is the practice curriculum that follows on from the BPF Performance Tools study notes and the Papy deep-dive. Each item below is a self-contained project: real code, a guidelines doc (how it works, how to build/run it), and an analysis doc (design decisions, trade-offs, what's simplified vs. a production system).

**Pacing:** same pattern as the book notes — one project built and verified at a time, delivered as soon as it's working, rather than everything half-built at once. Say "continue" for the next one.

## A note on what this environment can actually do

This all runs in a single, non-privileged cloud container — worth being upfront about what that means for each project, so nothing here is oversold:

| Capability | Available here? | Impact |
|---|---|---|
| C/C++ compilers (g++, clang), cmake, make | **Yes** | Anything pure-userspace-and-networking compiles and runs for real |
| TCP networking between local processes | **Yes** | Multi-process distributed algorithms (Raft, gRPC) run and are genuinely testable |
| Docker daemon / container runtime | **Yes, confirmed in Project 7** — `dockerd` isn't started by default, but starting it manually works completely: real containerd, real runc, real overlayfs, zero errors. The actual constraint turned out to be narrower and more specific than "daemon access not guaranteed": every container-registry host tested (`docker.io`, `ghcr.io`, `quay.io`, `registry.k8s.io`) is blocked by this sandbox's egress policy at the network level (confirmed 403 at the CONNECT step), while GitHub's own git protocol and release-asset CDN are allowlisted | A real single-node Kubernetes v1.31 control plane (via k3s, using only GitHub-release-distributed binaries/airgap images — no registry needed for k3s itself) genuinely comes up and is verified with `kubectl`; pulling any *other* image (Cilium's, in Project 7's case) hits the registry block directly, with the exact real rejection captured — see Project 7's ANALYSIS.md |
| Loading real eBPF programs into the live kernel (bpf() syscall) | **Yes, confirmed in Projects 4-5** — this sandbox's root user genuinely has the capabilities needed; BPF_PROG_LOAD itself was never the constraint. But this is attach-type-specific, not a blanket "BPF works here": Project 6 found a genuine hard wall for `sched_ext` specifically (`CONFIG_SCHED_CLASS_EXT` not set — a kernel build-time choice, not a privilege/tooling gap) | Projects 4 (tracepoints) and 5 (XDP/TC) both load real CO-RE programs and do real work; Project 6 compiles and attempts a real load of a real sched_ext scheduler and captures the kernel's real, specific rejection — each attach type genuinely has its own capability question, and this one came back "no," rigorously |
| A real Kubernetes control plane | **Yes, confirmed in Project 7** — this corrects the row below, which this project's own investigation proved wrong as stated. A real, single-node k8s v1.31 cluster (k3s) genuinely runs here. What's *not* available is any *workload* image from any container registry (see the Docker row above) — so a CNI like Cilium can be installed against a real cluster but can't finish pulling its own images here | See Project 7's README/ANALYSIS for the full story: real cluster, real install attempt, two distinct real stopping points (registry policy, and a separate cgroup-delegation limitation affecting any pod, not just Cilium's) |
| Linux capabilities (`CAP_*`) on this container | **40 of 41 standard capabilities are granted, confirmed in Project 8** — decoded directly from `/proc/self/status`'s `CapEff` bitmask, not inferred. `CAP_SYS_ADMIN`, `CAP_BPF`, `CAP_PERFMON`, `CAP_IPC_LOCK`, `CAP_NET_ADMIN`, and everything else needed for Projects 4-7's real eBPF/networking/container work are present. The **one** missing capability is `CAP_SYS_RESOURCE` | Blocks exactly one thing found so far: raising a resource limit's *hard* ceiling (e.g. `RLIMIT_MEMLOCK` past its current cap), which `parca-agent`'s eBPF loader requires unconditionally — see Project 8's ANALYSIS.md. Everything else that needed a privileged capability in Projects 1-7 worked |
| Go module fetches for non-GitHub vanity import paths (`google.golang.org/*`, `golang.org/x/*`, `cloud.google.com/go/*`) | **Blocked by the same egress policy as container registries, confirmed in Project 8, with a real scaling limit found in Project 9** — `go install`/`go get` resolve these by HTTP-GETing the vanity domain itself (e.g. `google.golang.org/grpc?go-get=1`) to discover the real backing repo, and that specific request gets a 403, same as `quay.io` in Project 7. Fixable per-dependency with `go.mod` `replace` directives pointing each blocked vanity import straight at its real GitHub mirror — demonstrated building `grpcurl` in Project 8 (8 blocked domains, converged in 2 rounds) and `netchaos` in Project 9 (1 blocked domain). But chaosd's build in Project 9 showed this doesn't scale to every dependency graph: 58 replace directives and 12 distinct blocked domains later, new domains were still surfacing with no sign of convergence, traced to an unconditional `sigs.k8s.io/controller-runtime` import pulling in the entire Kubernetes client stack | For a Go tool with a bounded dependency graph, this technique reliably works and is worth using (`verify/build-grpcurl.sh` in Project 8 is a reusable template). For one that transitively drags in a large, open-ended ecosystem, treat a growing, non-converging blocked-domain count as a real stopping point rather than something to keep patching indefinitely — `evidence/05-source-build-attempt-summary.md` in Project 9 documents exactly where and why to stop |
| Non-GitHub-Releases binary distribution for GitHub-hosted projects | **A real, recurring pattern, confirmed in Project 9** — not every tool that lives on GitHub ships its compiled binaries via GitHub Releases. `chaosd` uploads to an AWS S3 bucket behind `mirrors.chaos-mesh.org`; `helm` uploads to Azure Blob Storage behind `get.helm.sh` — both confirmed by reading each project's own release workflow YAML, not guessed. Both of those hosts are blocked by this sandbox's egress policy, same as the container registries in Project 7 | Before assuming a GitHub-hosted tool's binary is reachable here (the pattern that worked for k3s, cilium-cli, parca, parca-agent, stress-ng), check its actual release workflow for where binaries get uploaded — a clean 404 (not a 403) on a `releases/download/` URL guess is the tell that GitHub Releases is reachable but just isn't where this tool publishes, worth chasing down (e.g. via its own Makefile/CI config) before falling back to a source build |
| Kernel-level traffic control (`tc`/netem qdiscs via `RTM_NEWQDISC`) | **Confirmed absent in Project 9** — not a permissions gap: `CAP_NET_ADMIN` is present, and a real netlink client (`github.com/vishvananda/netlink`) gets a clean `ENOENT` from every non-default qdisc kind tried (`netem`, `prio`, `fq_codel`, `sfq`, `htb`, `tbf`). `/proc/kallsyms` confirms this directly — the core qdisc framework (`qdisc_alloc`, `register_qdisc`) is present, but zero scheduler implementations are compiled in, a genuine kernel build-time choice analogous to Project 6's `CONFIG_SCHED_CLASS_EXT` finding | Kernel-level network chaos/shaping (what Chaos Mesh's `NetworkChaos` CRD and the `tc` CLI both ultimately rely on) isn't available here. The real, working substitute is a userspace proxy applying the same delay/jitter/loss semantics in front of the target — a legitimate technique in its own right (it's how production tools like toxiproxy work), built and verified in Project 9 as `tcpchaos/` |
| Pod sandbox creation on this sandbox's container runtime | **Confirmed, with the cleanest reproduction yet, in Project 10** — Project 7 found this with Cilium specifically, leaving the CNI and image source as open confounds. Project 10 closed that gap: a fresh k3s cluster with its **default flannel CNI left on** (not disabled) reaches `Ready` normally, but k3s's own bundled CoreDNS pod — an image from k3s's airgap bundle, zero container registry contact at all — still fails identically: `runc create failed: unable to start container process: can't get final child's PID from pipe: EOF`. Same result on a real `istiod` pod. This rules out CNI choice and image/registry source as factors | **No pod can ever reach `Running` in this sandbox, for any workload, from any tool.** Don't spend time working around a specific image, CNI, or chart when a Kubernetes-native project's own workloads won't schedule here — the wall is the container runtime itself, confirmed project-agnostic across Projects 7, 9, and 10. A real control-plane piece of any K8s-native project (operators, service meshes, CNIs) is a documented-not-run finding by default; budget effort toward the data-plane/non-K8s pieces instead |
| GitHub Releases as a tool's actual binary distribution channel | **Inconsistent across projects — check per tool, don't assume** | Confirmed present (real GitHub-release binaries): k3s, cilium-cli, parca, parca-agent, stress-ng (Projects 7-9), and now `istioctl` (Project 10, `istio/istio`). Confirmed absent (ships via other cloud storage instead): `chaosd` (S3) and `helm` (Azure Blob Storage) (Project 9). Not correlated with how prominent or CNCF-official a project is — Istio uses GitHub Releases, Helm doesn't. Also worth knowing: GitHub's `releases/latest/download/<name>` redirect does tag substitution without checking the target asset exists — a wrong filename guess can 302 to a real-looking URL that then 404s, so confirm the actual asset name (via the repo's own release workflow, or by probing a few candidates) rather than trusting a successful-looking redirect alone |

Where a project can't be fully executed here, that's stated plainly in its own README rather than silently claimed as "done and tested."

| 11 | Raft-backed distributed KV store | **Built & verified** | Yes — fully executable, pure userspace, no environment caveats on the core result. Proven with a controlled A/B: the same `raft_node.cpp` compiled twice (`-DRAFT_UNSAFE_READS`), same scenario — a partitioned old leader serves a **stale read 3/3 times** with Project 1's local-only check and **refuses 3/3** with read-index. Read-index costs ~5× a local read (≈370 µs vs ≈72 µs p50 on loopback) — see its ANALYSIS.md |

## Why this order

Raft first because it's pure CS with zero infrastructure dependency — the single highest-leverage exercise in the field, per the original recommendation, and the best fit for your C++ background from Papy. Everything after it trades some real-execution confidence for closer ties to the modern eBPF/cloud-native stack discussed earlier; each project says so honestly rather than pretending otherwise.
